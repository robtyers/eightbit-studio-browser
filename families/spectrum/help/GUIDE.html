Spectrum development

Spectrum 48K, UK 128K and original grey UK +2 use the same original development emulator, guest BASIC firmware and Z80 assembler without supplied firmware or external tools when no external tools are selected. Browser Play also uses this runtime by default. Compatibility is bounded by the documented original-firmware interfaces; saved MAME settings and explicit MAME/SjASMPlus choices remain available. The Emulator panel can run the original runtime without changing those settings. Its separate native window and browser Game panel accept TAP or bounded PCM WAV input and record guest SAVE output to a checked TAP. BASIC statement and assembly instruction debugging use fresh source builds; source locations are invalidated if loaded bytes change. Other models retain their external tools.

This machine guide teaches Spectrum BASIC and Z80 assembly within Eightbit Studio’s implemented source workflow. Start with a Spectrum 48K project unless you specifically need another supported model. The 16K and 128K models have different memory or ROM requirements; choosing a name does not convert an existing project.

Choose a learning path

For BASIC, read Spectrum BASIC fundamentals, Decisions and loops, and Strings, arrays and data. Keep the statement and function references nearby. Then try Text and colours, Pixel graphics, Keyboard input and Sound before the complete Collect the stars project. The BASIC errors article explains what the emulated machine is reporting and how to repair common mistakes.

For assembly, first read the Z80 processor reference and addressing guide. Work through arithmetic and bounded loops before touching hardware. Read Spectrum memory and ROM calls, then build the complete Attribute banner project. The instruction reference covers every accepted documented mnemonic, with common forms and flag pitfalls. Spectrum 48K, UK 128K and original grey UK +2 support BASIC and assembly source debugging with the original runtime. External MAME assembly debugging remains limited to 48K.

Your first repeatable run

Choose New Project → ZX Spectrum → Spectrum 48K → Native BASIC. Select a new project folder. The generated README and tests/README describe the project’s source location and checks. Replace the active BASIC source with this original listing, Save, and Build. A BASIC build needs no external compiler.

10 BORDER 1
20 PAPER 0: INK 7: CLS
30 PRINT AT 5,3;"SPECTRUM WORKSHOP"
40 PRINT AT 7,3;"CHANGE A LINE AND RUN AGAIN"
50 STOP

Expected result: a blue border, black paper and two white text lines. STOP deliberately leaves the display available to inspect. Choose Run; a new Spectrum 48K, UK 128K or original grey UK +2 installation needs no ROM or emulator setup. If MAME is already selected, the Emulator panel’s Run original Spectrum action uses the built-in runtime without changing that choice. Loading is at native tape speed; allow it to finish. Enter complete BASIC commands or INPUT replies through BASIC command or input, or focus the screen for native keyword keys and game controls. With explicit MAME, keyboard input and sound belong to its external window. Build success alone does not prove that either text line appeared.

Change one thing and observe it

Change the row in line 30 from 5 to 6, Save and Run again. The first line should move down by one character row. Change only one value at a time so an unexpected result has a small set of causes. If you change to an invalid coordinate, note the machine’s report and restore the original. A build diagnostic is produced by Studio; a BASIC report displayed by the ROM is a different layer.

Export Media creates a TAP at a new destination; it does not write back into the source or overwrite an existing export. Run rebuilds the current source and cannot silently launch a previous successful build after failure. Opening a project does not build, run, access the network or use an AI provider. Those actions remain explicit.

Keep the target and dialect visible

Spectrum is not ZX81 BASIC and is not Commodore BASIC V2. Use LET for assignments, GO SUB/RETURN for routines and the Spectrum string-slicing forms. END, ELSE, LEFT$ and POKE addresses copied from another machine are not substitutes. The common Native BASIC page explains encoder boundaries; this machine section supplies the actual language lessons.

Use the Help section selector to stay in Spectrum plus shared Studio and Z80 topics. The 128K and peripherals article separates historical capabilities from the managed Studio session. Firmware, assembler macros, banked projects and unavailable devices cannot be enabled by copying a command from a reference entry.

Spectrum BASIC fundamentals

BASIC executes statements in line-number order unless a statement changes the flow. In Studio, type keywords as ordinary text; you do not need the original Spectrum keyboard’s token-entry keystrokes. Use line numbers separated by tens to leave room for additions. The editor row number is not the BASIC line number shown in a runtime report.

Values and assignments

10 LET score=120
20 LET bonus=25
30 LET n$="SAM"
40 LET score=score+bonus
50 PRINT n$;" SCORED ";score
60 STOP

The programme prints SAM SCORED followed by 145. In LET score=score+bonus, the right side reads the previous values and the left side receives the result. LET is required in Spectrum BASIC assignments. An equals sign in IF compares values instead. Unlike C64 variables, an ordinary Spectrum variable must be established before it is read; otherwise the ROM can report Variable not found.

Names and types

Simple numeric variable names begin with a letter and can continue with letters or digits. Use clear names such as score, lives and column. String variables use a single letter followed by $, such as n$. Numeric and string arrays also use a single-letter name; FOR control variables use a single letter. Spectrum does not use the Commodore integer % suffix. A scalar and an array of the same letter are distinct storage, but using them together can confuse a reader.

Numbers use floating-point arithmetic and may be written with decimal fractions or scientific notation. Strings hold character sequences in quotation marks. Put a quote inside a constructed string with CHR$ 34 rather than assuming another dialect’s quote escape. Source is ordinary ASCII; the character graphics and control-code source escapes are not implemented. You can produce runtime control characters through CHR$ where documented.

Expressions and comparisons

Arithmetic uses +, -, *, / and ^. Exponentiation binds more tightly than multiplication/division, which bind more tightly than addition/subtraction; unary minus also needs care around powers. Use parentheses when an expression combines operations, especially a negative base: (-2)^2 expresses a different intention from -(2^2). Comparisons use =, <, >, <=, >= and <> and normally yield 0 or 1.

String + concatenates. Comparing strings uses character-code order, not a locale-aware dictionary order. A numeric value and a string are different types: use STR$ for display composition and validated input before VAL. Floating-point calculations are approximate; use integer loop counters and compute a fractional position from the counter instead of repeatedly adding a fraction and expecting exact equality.

10 LET a=7: LET b=3
20 PRINT a+b;" ";a-b;" ";a*b
30 PRINT (a+b)*2
40 PRINT "HELLO "+"SPECTRUM"
50 PRINT a>b
60 STOP

Expected results are 10, 4 and 21 on the first line, then 20, HELLO SPECTRUM and 1. Each colon separates statements. Put LET before both assignments in line 10. The whitespace in a quoted string is data; changing keyword case does not intentionally change quoted output.

Printing deliberately

PRINT starts a new line unless you leave a trailing separator. A semicolon joins output without a print-zone advance; a comma selects the next print zone; an apostrophe in the PRINT item list starts a new line. That apostrophe is not a general comment character. PRINT AT row,column uses character coordinates with row zero at the top; PRINT TAB column moves within a line. The screen article explains colour and coordinate limits.

Build limits and runtime checks

Use increasing line numbers 1–9999, up to 4096 bytes in a physical line and up to 128 KiB source. The encoded BASIC budget is 7000 bytes on Spectrum 16K and 40000 on the other registered models. Variables and arrays consume additional runtime space. REM makes the rest of the physical line comment text, including a later colon.

Studio validates tokenisation, quotes, numbers and packaging; the ROM remains the full syntax and runtime authority. A successfully encoded IF with a bad expression can still fail at runtime. Spectrum DEF FN definitions are supported; graphical source escapes remain unavailable. These lessons use the subset that can be encoded through the actual source workflow.

Spectrum decisions, loops and subroutines

Control flow decides which statement runs next. Begin with short branches and a visible exit condition. A programme that prints forever can be valid BASIC while still being difficult to use. Keep the normal path readable and move reusable work to clearly separated subroutine lines.

IF controls the remainder of a line

10 INPUT "SCORE? ";s
20 IF s<0 THEN PRINT "USE ZERO OR MORE": GO TO 10
30 IF s>=100 THEN PRINT "BONUS EARNED"
40 IF s<100 THEN PRINT "KEEP TRYING"
50 STOP

Try -1, 50 and 100. A false condition skips the rest of that line. In line 20, both PRINT and GO TO belong to the true branch because they follow THEN on the same physical line. There is no Spectrum ELSE keyword in this workflow. Use separate branches or GO TO when you need two exclusive paths. A bare line number after THEN is not the form used here; write an explicit GO TO.

AND, OR and NOT can combine comparisons, but Spectrum’s operators also have numeric conditional behaviour. For simple decisions, put parentheses around each comparison and use their 0/1 results. Do not assume short-circuit evaluation protects an invalid division or array subscript: validate the prerequisite in a separate IF before computing the risky expression.

Counted repetition

10 FOR n=5 TO 1 STEP -1
20 PRINT n
30 NEXT n
40 PRINT "DONE"
50 STOP

This prints 5 through 1, then DONE. The limit is inclusive when the count reaches it. STEP defaults to one; a negative step counts down. Use a one-letter numeric control variable. A zero step can produce a non-terminating loop, and changing the loop variable inside the loop makes its lifetime harder to understand. Keep nested loop variables distinct and pair each NEXT with its intended FOR.

A loop that is initially out of range skips forward to its matching NEXT. A missing match can therefore report FOR without NEXT even though the loop body was meant to run zero times. Test both an empty range and a one-iteration range in a data-driven routine.

Polling with an explicit exit

10 PRINT "PRESS Q TO FINISH"
20 LET k$=INKEY$
30 IF k$="q" OR k$="Q" THEN GO TO 70
40 PAUSE 1
50 GO TO 20
70 PRINT "FINISHED"
80 STOP

INKEY$ is empty when no ordinary key is detected. PAUSE 1 keeps the loop from being a pure busy poll, but a key can shorten a pause. Focus the active emulator before trying it. This programme exits on Q and does not depend on a Studio UI key event. If a programme becomes unresponsive, Studio Stop ends the emulator session.

Subroutines and shared variables

10 LET s=0
20 GO SUB 100
30 LET s=s+10
40 GO SUB 100
50 STOP
100 PRINT "SCORE=";s
110 RETURN

The subroutine prints SCORE=0 and then SCORE=10. GO SUB remembers where to return; GO TO does not. STOP at line 50 prevents normal flow falling into line 100 and reaching RETURN with no caller. Variables are shared globally, so a subroutine that changes s changes the caller’s score. State which variables are inputs and which may change.

Nested GO SUB calls consume memory for return state. An accidental GO SUB in a loop where GO TO was intended can grow that state without ever returning. Use one entry and one return while learning. When adding an early-exit branch, make sure it returns rather than jumping back into the main loop and abandoning a pending call.

Experiments and recovery

Change the countdown to start at one, then zero, and explain the resulting iterations. Add a second score-display call after a subtraction and predict the output before running. Deliberately change GO SUB 100 to GO TO 100 to observe RETURN without GO SUB, then repair the call. Record the BASIC line and statement numbers, not just “it stopped”.

RUN restarts a BASIC programme and clears its variables. CONTINUE attempts to resume after certain stops, with report-specific rules; it is not a substitute for a clean rerun after arbitrary edits. Studio Run starts a fresh managed build and machine session, so persistent game state must be designed explicitly rather than assumed.

Spectrum strings, arrays and data

Use strings for text and arrays for indexed collections. Decide the maximum size before allocating an array, especially on Spectrum 16K. BASIC variables and temporary strings share the available memory with your programme; fitting the encoded source does not guarantee that a large DIM will succeed at runtime.

Strings and slicing

10 LET a$="SPECTRUM"
20 PRINT LEN a$
30 PRINT a$(1 TO 4)
40 PRINT a$(5 TO)
50 LET a$(1 TO 4)="STAR"
60 PRINT a$
70 STOP

Expected output: 8, SPEC, TRUM and STARTRUM. String positions are one-based, unlike PRINT AT coordinates. A slice selects a range using TO; an omitted endpoint means the corresponding end of the string. A selected fixed-length substring is replaced within its existing extent, with padding or truncation as required. Assigning the whole string can change its length. Use LEN before calculating a position derived from input.

There are no LEFT$, MID$ or RIGHT$ functions in Spectrum BASIC. Use a$( TO n), a$(first TO last) and a$(first TO) after validating the range. CODE reads the code of the first character, not a whole numeric string. CHR$ makes a character from a code. STR$ converts a number to text; VAL evaluates a numeric expression contained in text and can fail on invalid input.

Numeric arrays

10 DIM a(4)
20 FOR n=1 TO 4
30 LET a(n)=n*n
40 NEXT n
50 LET t=0
60 FOR n=1 TO 4
70 LET t=t+a(n)
80 NEXT n
90 PRINT "TOTAL=";t
100 STOP

The four entries are 1, 4, 9 and 16; the total is 30. DIM a(4) makes positions 1–4, not 0–3. DIM a(2,3) creates six numeric entries addressed with two indices. Use the same index count as the declaration. Redimensioning an array replaces its previous values; it is not a storage-preserving resize operation.

String arrays have a length dimension

10 DIM n$(3,8)
20 LET n$(1)="SAM"
30 LET n$(2)="JO"
40 LET n$(3)="ALEX"
50 FOR i=1 TO 3
60 PRINT i;" ";n$(i)
70 NEXT i
80 STOP

This creates three eight-character records, initially spaces. The last dimension is each string’s length. Short assignments are padded; long assignments are truncated. n$(2) selects the second complete record, while an additional character index or slice selects within it. DIM a$(8) is one fixed-length string, not eight independently sized strings. Plan input limits so truncation is intentional and visible.

Data and its read position

10 DATA 3,6,9,12
20 LET t=0
30 FOR n=1 TO 4
40 READ v
50 LET t=t+v
60 NEXT n
70 PRINT t
80 RESTORE 10
90 READ v
100 PRINT v
110 STOP

This prints 30 then 3. READ advances through DATA items; RESTORE resets where future reads begin, optionally at a line. Numeric and string destinations must match their items. RESTORE does not clear an array or undo arithmetic. If a fifth READ runs here before RESTORE, it exhausts the data. Put a count beside a data table or use a deliberate sentinel and validate it.

Input as text before conversion

INPUT LINE a$ accepts text without treating it as a numeric expression. To accept a single digit, require LEN a$=1, then compare CODE a$ with 48 and 57. Only after both checks should VAL a$ be used. Check length in an earlier statement rather than assuming AND will avoid evaluating a missing character. For a larger number, validate each character and a length bound before conversion.

Exercise: change the square table to six entries and update both loops. Add a maximum score and reject values outside it before storing them. Test the first valid index, the last valid index and an invalid index zero. Each experiment should have a predicted result and a repair path; the runtime error article explains Subscript wrong and Variable not found.

Spectrum BASIC statement reference

Use this alphabetical reference for forms, meaning and the important distinction between a language token and an available Studio workflow. Examples on this page are statement forms, not necessarily complete programmes. The tutorials and projects contain complete copyable listings. A successful Build checks encoding; the ROM checks full syntax and runtime state.

Statements and device boundaries

Entries marked historical or peripheral-dependent describe vocabulary recognised by the encoder without promising that the managed MAME session supplies the device. Spectrum DEF FN definitions can be built from source. BASIC LOAD/SAVE are not host file APIs. Prefer ordinary display, input and calculation statements in first programmes.

BEEP

Form: BEEP duration,pitch.

Play a tone for a duration in seconds; pitch is measured in semitones relative to middle C. The normal range is -60 through 69, and duration must be nonnegative. BEEP 0.1,7 is a short fifth. It blocks programme progress while sounding. Read Sound for a bounded tune and emulator audio checks.

BORDER

Form: BORDER colour.

Set the border to a colour 0–7; BORDER 1 selects blue. It does not change the paper inside the text screen. Brightness and flash attributes do not apply to the border. Restore a chosen neutral border before finishing a demonstration that changes it repeatedly.

BRIGHT

Form: BRIGHT 0; BRIGHT 1.

Select normal or bright attributes for subsequent display output; 8 preserves the existing brightness where that special value is accepted. It does not make independent foreground and background brightness values within one character cell. Set it explicitly before a graphics lesson rather than inheriting previous state.

CAT

Form: CAT! in 128 BASIC.

Lists the original 128K or grey +2 RAM disc alphabetically. The separate historical CAT form requires a Microdrive interface, which Studio does not attach. Export Media saves the source programme artefact to a host destination.

CIRCLE

Form: CIRCLE x,y,r.

Draw a circle with centre x,y and radius r in BASIC graphics coordinates. Use a positive radius and keep the full shape inside the drawing area while learning. CIRCLE 128,88,30 is a bounded example. Pixel graphics explains the difference between these coordinates and character rows.

CLEAR

Form: CLEAR; CLEAR address.

Clear variables and runtime state; the address form also sets the upper limit for BASIC’s working memory. The assembly loader uses CLEAR 24575 to reserve code at 24576. An unsuitable limit reports RAMTOP no good. Do not lower it beneath a running programme’s storage or use it as a substitute for array bounds.

CLOSE #

Form: CLOSE #stream.

Close a stream association. Streams and their attached channels belong to the ROM/peripheral environment, not Studio filesystem handles. Closing a channel in use by display or input can make subsequent statements fail. The managed workflow does not supply general peripheral channel configuration.

CLS

Form: CLS.

Clear the display using the current permanent screen attributes and reset the text position. Set PAPER and INK first when you want a predictable background. CLS does not clear variables or restart your programme. A blank screen after CLS can mean subsequent text uses the same ink and paper.

CONTINUE

Form: CONTINUE.

Resume according to the preceding BASIC report’s saved position. STOP normally continues after the stop; break and input reports have distinct repeat rules. It does not recreate lost variables or repair edited-away statements. For a reproducible Studio test, Save and Run the corrected source afresh.

COPY

Form: COPY.

Historical ZX Printer screen-copy operation. Studio does not attach a printer or capture its output through this command. It is unrelated to copying text in the editor or exporting a TAP. Treat it as device-dependent reference vocabulary.

DATA

Form: DATA 3,6,"RED".

Define expressions or string items consumed by READ; execution flow normally passes over DATA. Keep the destination types and number of reads in agreement with the table. DATA is not a comment: use quoted strings for text and REM for prose. RESTORE changes the next read location.

DEF FN

Form: DEF FN f(x)=x*x.

Define a reusable numeric or string function. The function and each parameter use a single letter, optionally followed by $. Calls use FN and brackets, including an empty pair for a function without parameters. Match argument types and count to the definition.

DIM

Form: DIM a(10); DIM n$(5,12).

Allocate an array with one-based indices. The last dimension of a string array is the fixed character length. Numeric elements start at zero and string storage at spaces. Repeating DIM discards previous contents. Count the runtime storage as well as the encoded source budget.

DRAW

Form: DRAW dx,dy; DRAW dx,dy,angle.

Draw relative to the current graphics position. The two-operand form makes a line; an optional angle specifies an arc in radians. Begin with a known PLOT position. Unlike PRINT AT, these are pixel displacements, and positive y goes upwards. Keep every endpoint and arc within bounds.

ERASE

Form: ERASE! "name" in 128 BASIC.

Removes a RAM-disc file and reclaims its storage in the original UK 128K and grey +2 runtime. The separate historical ERASE form requires an attached peripheral. Neither form removes host source, exports or project data.

FLASH

Form: FLASH 0; FLASH 1.

Choose steady or flashing attributes; 8 preserves the existing setting where accepted. Flash swaps the cell’s ink and paper appearance periodically; it is not independent sprite animation. Prefer FLASH 0 for steady tutorial output and do not rely on flashing colour as the only meaning carrier.

FOR

Form: FOR n=1 TO 10 STEP 2.

Create a counted loop with a single-letter numeric control variable, inclusive limit and optional step. Match NEXT n and avoid STEP 0. If the initial range executes no iterations, BASIC still needs to find its matching NEXT. See Decisions and loops for descending and empty-range examples.

FORMAT

Form: FORMAT.

Historical interface/peripheral formatting command, with device-dependent operands. It is not supported as a managed Studio storage workflow. Never interpret this vocabulary entry as an instruction to format a host disk or emulator medium. Use the exact peripheral manual only in a separately configured historical environment.

GO SUB

Form: GO SUB 500.

Call a numbered subroutine, saving where RETURN should resume. Variables are shared rather than local. Put STOP or a branch before the routine area to prevent accidental fall-through. Repeated calls that never return consume memory. GOSUB is an accepted Studio spelling alias.

GO TO

Form: GO TO 200.

Continue at the requested programme line, without saving a return address. BASIC searches for the next line at or after a numeric target, so a missing exact destination may not behave like an assembler’s undefined label. Use actual existing destinations for clarity. GOTO is an accepted Studio alias.

IF

Form: IF condition THEN statement.

Execute the remainder of the physical line when the condition is nonzero; otherwise continue at the next line. A colon after THEN remains part of that conditional tail. There is no ELSE. Write IF s=0 THEN GO TO 200 for an explicit branch rather than borrowing another BASIC dialect’s shorthand.

INK

Form: INK colour.

Set the ink for later output. Ordinary colours are 0–7; special values 8 and 9 preserve or contrast where supported. INK 7 with PAPER 0 gives white on black. Changing a text cell’s ink affects its bitmap pixels collectively because Spectrum colour belongs to an eight-by-eight cell.

INPUT

Form: INPUT "NAME? ";a$; INPUT LINE a$.

Read a value or string through the ROM input system. INPUT LINE reads text without expression evaluation. Use the built-in BASIC command or input field, or focus the emulated screen for native keys. With explicit MAME, focus its window before typing. For numeric data, reject out-of-range values before using them as array indices or addresses. Invalid input can fail at runtime even when the programme encodes correctly.

INVERSE

Form: INVERSE 0; INVERSE 1.

Choose ordinary or inverse character/graphics output. INVERSE changes which drawn bits are treated as ink; it is distinct from choosing different colour numbers with INK and PAPER. Set INVERSE 0 before a normal lesson so inherited display state does not reverse its output. Combine with OVER only after testing each operation separately.

LET

Form: LET score=score+10.

Assign the evaluated right-hand value to the named variable, array element or valid substring. LET is explicit in Spectrum source. Establish a variable before reading it. Assigning a string to a numeric destination is not an implicit conversion; use suitable types and validated conversion routines.

LIST

Form: LIST; LIST 100.

Display the programme, optionally starting near a numbered line, on the emulated machine. It does not synchronise ROM-side edits back to Studio. Keep the saved source as the authoritative programme and rerun after experiments in the emulator. LLIST is the historical printer counterpart.

LLIST

Form: LLIST; LLIST 100.

Historical listing to the printer channel. No printer is configured by Studio’s managed Spectrum session. This does not print the editor or create a host file. Use LIST for an on-machine inspection and the editor for source review.

LOAD

Form: LOAD ""; LOAD "name" CODE.

Historical cassette loading, optionally with data-type qualifiers. Studio’s generated assembly loader uses LOAD "" CODE as part of its fixed tape sequence. General media import/editing and arbitrary device setup are not added by this command. Run supplies the managed TAP; wait for loading to finish.

LPRINT

Form: LPRINT "TEXT".

Historical output to the printer stream. It has PRINT-like formatting but requires the appropriate device/channel. Studio does not capture a printout or expose host printing through BASIC. Use PRINT when testing visible programme text in the managed emulator.

MERGE

Form: MERGE "name".

Historical merge of BASIC lines from cassette into an existing in-memory programme. It is not a Studio multi-file source feature, Git merge or project import. ROM-side merged content is not written back into the saved project. Use it only in a separately managed historical tape exercise.

MOVE

Form: MOVE.

Historical interface command to transfer data between peripheral streams, using device-specific syntax. It is unrelated to moving a sprite or source file. No corresponding peripheral routing is configured by Studio. Consult the appropriate hardware manual outside this managed workflow.

NEW

Form: NEW.

Discard the current in-memory BASIC programme and reset its state. This is an emulator operation, not the Studio New Project action. It does not delete your saved source, but it can discard ROM-side edits that were never exported. Use Run to reload the saved project deliberately.

NEXT

Form: NEXT n.

Advance the matching FOR control variable and repeat while it remains in range. It is not an increment statement for an arbitrary variable. Keep the loop variable single-letter, nesting clear and matching FOR reachable. A wrong or absent loop context causes a runtime report.

OPEN #

Form: OPEN #stream,channel.

Associate a stream number with a channel supported by the active ROM/peripheral environment. Token acceptance does not supply a printer, Microdrive or network. It does not open arbitrary host files. The introductory examples retain the ordinary screen and keyboard channels.

OUT

Form: OUT port,value.

Write a byte to a hardware I/O port. Port addresses and combined bit meanings are machine-specific. This can alter border, sound or memory mapping rather than ordinary variables. Validate both operands, preserve unrelated register bits and avoid paging experiments in the managed unbanked source project.

OVER

Form: OVER 0; OVER 1.

Choose ordinary drawing or XOR-style overprinting. Drawing the same pixel pattern twice with OVER 1 can restore its previous pixels, but attribute changes are a separate concern. Use OVER 0 before a fresh static lesson. OVER accepts only 0 or 1; it does not support the transparent value used by some colour controls.

PAPER

Form: PAPER colour.

Set paper for later output, normally 0–7; 8 and 9 have preserve/contrast meanings where accepted. PAPER changes permanent output state; CLS applies it across the cleared screen. Equal ink and paper can hide otherwise correct text. Brightness is shared by the cell’s colours.

PAUSE

Form: PAUSE frames.

Wait for a number of display frames or a key. On these PAL profiles 50 frames is approximately one second. PAUSE 0 waits for a key, not zero time. A held key can shorten a pause, so it is not a guaranteed high-precision timer or a universal input debounce.

PLOT

Form: PLOT x,y.

Set or combine a pixel according to current graphics attributes and OVER/INVERSE state, establishing the graphics position for DRAW. BASIC uses x=0–255 and y=0–175 with y increasing upwards. PRINT AT uses rows and columns instead. Keep the axes explicit in variable names.

POKE

Form: POKE address,value.

Write a byte 0–255 to a validated RAM address. A legal numeric address can still be ROM, screen, programme, system or stack storage. POKE 22528,71 changes the first screen attribute; it does not draw a character bitmap. Read Memory before using addresses from another listing.

PRINT

Form: PRINT "SCORE=";s.

Write values to the screen using separators and optional temporary display controls. AT row,column places text; TAB selects a column. A semicolon joins items, comma uses print zones and apostrophe starts a line. See Text and colours for row limits and avoiding a scroll prompt during animation.

RANDOMIZE

Form: RANDOMIZE; RANDOMIZE 123.

Set the pseudo-random generator seed. A fixed nonzero seed makes a sequence reproducible; the no-argument/zero form uses timing state. RANDOMIZE USR 24576 is also used by the native assembly loader to call code. RANDOMISE is a Studio spelling alias.

READ

Form: READ a,b$.

Consume successive DATA items into destinations with matching types. Exhausting items reports Out of DATA. Keep the item count or terminator explicit and do not assume a failed read silently returns zero. RESTORE changes the read pointer without re-running your whole programme.

REM

Form: REM EXPLANATION.

Treat the rest of the physical line as comment text. A colon inside REM does not start another executable statement. Use REM for source explanations and keep data in DATA. Studio preserves comment text rather than interpreting it as a set of keyword tokens.

RESTORE

Form: RESTORE; RESTORE 200.

Reset the DATA read position to the start or to the first DATA at or after a requested line. This differs from dialects whose RESTORE has no argument. It does not restore variables to earlier values. Use a known line at the beginning of a table.

RETURN

Form: RETURN.

Resume the saved location from a preceding GO SUB. It is not an exit from FOR or a general end-of-programme marker. STOP or a branch should separate the main programme from its routine area. Every possible routine exit must preserve the pending return structure.

RUN

Form: RUN; RUN 100.

Start the in-memory BASIC programme, optionally at a line, clearing its variables. Starting after initialisation can cause missing-variable errors. Studio’s Run button is broader: it saves only through the explicit source workflow, builds and starts a fresh managed emulator session with the project’s media.

SAVE

Form: SAVE "name"; SAVE "name" LINE 10.

Historical cassette output, optionally with a BASIC autostart line or data qualifiers. Use a valid short tape name. Studio Export Media writes a new TAP from the built programme and is the supported host export workflow; BASIC SAVE does not silently create a host file or editor backup.

STOP

Form: STOP.

Stop BASIC deliberately, normally reporting code 9. It is useful before a subroutine area or after displaying a result. CONTINUE can proceed after it in the machine environment. Studio Stop terminates an owned emulator/debug session and is a separate control.

VERIFY

Form: VERIFY "name".

Historical cassette comparison against memory. Tape errors or mismatched content can produce a report. Studio’s build freshness hashes and Export Media checks are separate from VERIFY, and no general tape-management UI is supplied by this command. Keep a freshly built export as the reproducible artefact.

Qualifiers, aliases and later models

THEN introduces the IF tail; TO separates loop limits and slice endpoints; STEP supplies a FOR increment. LINE is used in INPUT LINE and SAVE LINE forms rather than drawing a line. AT and TAB are PRINT/INPUT layout controls. CODE and DATA also qualify historical tape operations.

GOTO, GOSUB and RANDOMISE are accepted source aliases for GO TO, GO SUB and RANDOMIZE. Full spaced forms make the connection to the original language clearer. On UK 128K and original grey +2 only, the encoder additionally recognises PLAY and SPECTRUM. See Models and peripherals before using these; they are not baseline 16K/48K statements.

Spectrum BASIC functions and operators

A function yields a value that a surrounding expression uses. Parentheses make composed arguments clear even where the language allows them to be omitted. The entries below cover the baseline Spectrum token vocabulary, with domains, small calculations and input pitfalls. Device-related functions retain their machine restrictions.

Numeric, string and hardware functions

ABS

Form: ABS x.

Return magnitude. ABS -7 gives 7. It is useful for distance or an error size, but it removes direction; preserve the original signed value when direction matters.

ACS

Form: ACS x.

Inverse cosine in radians for x between -1 and 1. ACS 1 gives zero. Reject values outside the mathematical domain rather than assuming the ROM clamps them.

ASN

Form: ASN x.

Inverse sine in radians for x from -1 to 1. ASN 0 gives zero. Floating-point rounding can push a computed value slightly outside the domain; validate calculations before using it.

ATN

Form: ATN x.

Inverse tangent in radians. ATN 1 is approximately PI/4. It does not by itself resolve the full quadrant of a two-coordinate vector; handle signs and zero denominators deliberately.

ATTR

Form: ATTR (row,column).

Read the attribute byte of a character cell. Decode ink, paper, bright and flash separately; the whole byte is not a colour number. Use rows 0–23 and columns 0–31 within the physical screen.

BIN

Form: BIN 101010.

Introduce a binary numeric literal; this example is decimal 42. It helps describe bit masks. It is not a string conversion function and does not turn an arbitrary text variable into a binary number.

CHR$

Form: CHR$ code.

Make a one-character string from code 0–255. PRINT CHR$ 34 produces a quotation mark. Runtime control characters can affect display state; ordinary ASCII source does not accept graphical escape sequences.

CODE

Form: CODE a$.

Read the first character’s code. CODE "A" is 65. Check LEN before processing input; one character’s code is not the numeric value of a multi-digit string. It also appears as a historical tape qualifier.

COS

Form: COS x.

Cosine of an angle measured in radians. COS 0 is 1. To use degrees, convert with degrees*PI/180. Keep the conversion explicit when a user supplies an angle.

EXP

Form: EXP x.

Calculate e raised to x. EXP 0 is 1. Large positive inputs can overflow, while very small results may lose useful precision. Bound user inputs before making exponential calculations.

FN

Form: FN f(x).

Call a function declared with DEF FN. Supply the declared number and types of arguments in brackets. Numeric and string parameters belong to the call, so give shared global variables distinct names when that makes the programme clearer.

IN

Form: IN port.

Read a byte from an I/O port. The returned bits are hardware-specific and may be active-low. It is not PEEK: memory addresses and ports are separate spaces. Keyboard matrix scanning is covered in the input article.

INKEY$

Form: INKEY$.

Return the current detected character, or an empty string when none is available. It does not wait for a complete line. Handle held keys and emulator focus. It is suitable for simple single-key games, not a universal multi-key keyboard-state API.

INT

Form: INT x.

Round down to the greatest integer no larger than x. INT -1.2 is -2, not -1. INT (RND*6)+1 gives a value from one through six. Put parentheses around a composed argument for readability.

LEN

Form: LEN a$.

Return the number of characters. Spaces count, including padding in fixed-width string arrays. Check LEN before slicing or accepting a bounded name, and do not confuse display width with the size of a control-code sequence.

LN

Form: LN x.

Natural logarithm for x greater than zero. LN 1 is zero. Zero and negative arguments are invalid. Guard the domain in a preceding statement rather than assuming a compound Boolean condition suppresses evaluation.

PEEK

Form: PEEK address.

Read a byte at a memory address in the current mapping. Combine PEEK a+256*PEEK (a+1) for a little-endian word, with suitable parentheses. A system variable can change between reads; avoid treating arbitrary live memory as a stable table.

PI

Form: PI.

The mathematical constant used with trigonometric functions and arc angles. PRINT PI shows an approximate decimal representation. It is not a variable name to assign or a unit conversion by itself.

POINT

Form: POINT (x,y).

Read whether a pixel is set in the BASIC graphics area. The result concerns the bitmap, not the attribute ink/paper value or an object identity. Track game objects in variables instead of relying only on screen collisions.

RND

Form: RND.

Produce a pseudo-random fraction from zero inclusive to one exclusive. Use INT (RND*n) for zero-based choices with positive n. A fixed RANDOMIZE seed makes experiments repeatable; it is not appropriate for security or unpredictable secrets.

SCREEN$

Form: SCREEN$ (row,column).

Attempt to recognise the character at a screen cell and return its string. Arbitrary graphics need not correspond to a recognisable character. It is not a copy of the entire screen and does not return the cell’s attribute byte.

SGN

Form: SGN x.

Return -1 for a negative value, 0 for zero or 1 for positive. It separates direction from magnitude. SGN target-position can suggest a unit movement, but parentheses are needed if the whole difference is intended as the argument.

SIN

Form: SIN x.

Sine of x radians. SIN (PI/2) is approximately 1. Convert degrees explicitly, and allow tolerance when testing floating-point values rather than requiring exact equality with a displayed rounded result.

SQR

Form: SQR x.

Square root for nonnegative x. SQR 81 gives 9. It does not produce complex numbers for negative inputs. Check a computed squared-distance expression for arithmetic mistakes before passing it on.

STR$

Form: STR$ x.

Convert a number to its text representation. It is useful for concatenating a label and a score. The result can vary in length as a number grows, so clear or overwrite the remaining display field when updating in place.

TAN

Form: TAN x.

Tangent of x radians. Values near odd multiples of PI/2 are unstable or undefined mathematically. Choose a bounded interval for user-facing calculations rather than relying on a huge floating-point result near a pole.

USR

Form: USR address; USR "a".

The numeric form calls machine code and returns a value derived from BC. The string form finds a user-defined graphic character’s storage in the relevant ROM mode. They are different operations. Only call code at a valid, loaded entry with a safe return convention.

VAL

Form: VAL a$.

Evaluate a numeric expression contained in a string. It accepts more than decimal digits, so it is not input validation. Invalid text can report Nonsense in BASIC. Validate a bounded digit format before converting a value that will become a coordinate, index or address.

VAL$

Form: VAL$ a$.

Evaluate text representing a string expression. Quoting and expression syntax must be valid; it is not the same as returning the input string unchanged. Avoid it in simple input flows where the user should supply data rather than expressions.

Operators and layout keywords

NOT maps zero to one and nonzero to zero. The AND and OR operators have conditional semantics. For numeric x, x AND y yields x when y is nonzero and zero otherwise; x OR y yields one when y is nonzero and x otherwise. Thus these are not Z80 bitwise masks. In ordinary comparisons using 0/1 values they act as familiar logical operators. String AND has a conditional-string form; keep such compact expressions out of beginner code when IF is clearer.

<=, >= and <> compare values for less-or-equal, greater-or-equal and unequal. Arithmetic and comparisons should be parenthesised before combining with NOT, AND and OR. Never rely on a compound condition to guard an invalid function argument; validate its prerequisites first.

AT takes row,column in a PRINT/INPUT list; TAB takes a column and can wrap to another line. They control layout rather than returning a general numeric result. The PRINT apostrophe starts a new line, a semicolon avoids a print-zone advance and a comma selects the next zone.

A repeatable random experiment

10 RANDOMIZE 123
20 FOR n=1 TO 6
30 PRINT INT (RND*6)+1
40 NEXT n
50 STOP

Every value should lie between one and six, and rerunning with the same fixed seed should reproduce the sequence. Six rolls are not guaranteed to contain every face. Change the upper multiplier only after deciding the intended inclusive bounds. An off-by-one error can turn a random choice into an invalid array subscript.

Spectrum BASIC reports and recovery

Read the report on the emulated Spectrum, including its BASIC line and statement number. A report identifies the place where the ROM noticed a problem; the cause may be an earlier assignment or branch. Studio diagnostics such as DSS1110 concern source encoding or tool boundaries and are not these ROM reports.

Use a repeatable repair cycle

Stop the session if necessary, locate the numbered line in saved source, make one change, Save and Run again from initialisation. Record the input that caused the failure and the expected repaired result. The standard report vocabulary below includes successful stops and historical peripheral reports; it does not imply that every peripheral is provided by Studio.

0: OK

Cause: Normal completion, including reaching beyond the last line.

Example: A programme reaches its final statement.

Recovery: Treat it as success only after checking the expected output; a premature jump can also reach completion.

1: NEXT without FOR

Cause: NEXT has no matching active loop context.

Example: LET n=1 followed by NEXT n is not a FOR loop.

Recovery: Restore the matching FOR and its control variable. Check branches that skip initialisation.

2: Variable not found

Cause: A variable has not been established or an array has not been dimensioned.

Example: PRINT score before LET score=0.

Recovery: Initialise before first read; start tests from the beginning and check variable spelling and type.

3: Subscript wrong

Cause: An index, slice or number of array dimensions is unsuitable.

Example: DIM a(3) followed by PRINT a(4).

Recovery: Use one-based indices within each declared dimension. Check LEN before deriving a string slice.

4: Out of memory

Cause: The programme, variables, arrays, expression workspace or return state exceed available RAM.

Example: A large DIM on the 16K model.

Recovery: Reduce allocation and temporary strings, repair unreturned GO SUB loops and rerun cleanly. Source-size acceptance is not a runtime memory guarantee.

5: Out of screen

Cause: Output or input placement exceeds the ROM display area.

Example: PRINT AT 22,0 in ordinary upper-screen output.

Recovery: Keep tutorial text rows 0–21 and columns 0–31. Reduce input prompt height and distinguish text coordinates from pixels.

6: Number too big

Cause: An arithmetic result is outside the numeric range.

Example: Repeatedly multiplying a large number by ten.

Recovery: Bound inputs and intermediate results, or reformulate the calculation before overflow. Smaller printed precision does not reduce the internal magnitude.

7: RETURN without GO SUB

Cause: RETURN has no saved subroutine caller.

Example: Execution falls from the main programme into the routine area.

Recovery: Put STOP or a branch before subroutines and enter with GO SUB, not GO TO.

8: End of file

Cause: A peripheral read has reached the end of its input.

Example: A historical channel-based file read exhausts its records.

Recovery: Use the device’s end-of-data convention. Managed Studio does not configure this peripheral workflow; it is unrelated to BASIC DATA exhaustion.

9: STOP statement

Cause: The programme deliberately executes STOP.

Example: A tutorial ends after displaying its result.

Recovery: Inspect the result; this can be expected. On the machine, CONTINUE normally resumes after STOP. Studio Stop is a different control.

A: Invalid argument

Cause: A function receives a value outside its domain.

Example: SQR -1 or LN 0.

Recovery: Validate the domain in an earlier statement. Check whether a calculation should have produced a positive value.

B: Integer out of range

Cause: A value used as an integer is outside the operation’s accepted range.

Example: POKE 22528,300.

Recovery: Check address, byte, character, coordinate or index bounds before use. Rounding a fractional input does not make an excessive value valid.

C: Nonsense in BASIC

Cause: An evaluated textual expression is invalid BASIC.

Example: VAL "APPLE".

Recovery: Validate input as bounded data before VAL/VAL$. Also inspect statement punctuation when the ROM rejects programme syntax.

D: BREAK - CONT repeats

Cause: An operation was interrupted where continuation would repeat the current statement.

Example: Breaking a historical tape or printer operation.

Recovery: Check whether repeating that operation is appropriate before CONTINUE. Prefer a fresh managed Run for a deterministic development test.

E: Out of DATA

Cause: READ asks for an item after the available DATA.

Example: Five READ operations for four items.

Recovery: Match count to table length or RESTORE the intended table before rereading. Do not add a dummy value without fixing the loop’s meaning.

F: Invalid file name

Cause: A historical SAVE name is empty or exceeds the accepted tape-name length.

Example: SAVE with an empty name.

Recovery: Use a nonempty name of at most ten characters for the historical command. Studio’s host export destination is a separate naming boundary.

G: No room for line

Cause: The machine cannot store another edited BASIC line.

Example: Adding a long line when in-memory programme space is exhausted.

Recovery: Recover your source in Studio, reduce the programme or use a suitable target. ROM-side edits are not automatically saved back.

H: STOP in INPUT

Cause: Input was stopped rather than successfully supplying the requested value.

Example: Entering STOP during the machine’s input workflow.

Recovery: Retry the input or rerun deliberately. Continuation can repeat the INPUT, so do not assume a new variable value was stored.

I: FOR without NEXT

Cause: A skipped FOR body has no discoverable matching NEXT.

Example: FOR n=1 TO 0 with its NEXT missing.

Recovery: Provide a correctly nested NEXT even for an initially empty range. Test zero-iteration paths as well as the normal loop.

J: Invalid I/O device

Cause: A historical peripheral selection is not valid for the environment.

Example: A channel names an unavailable device.

Recovery: Use the appropriate peripheral configuration outside the managed workflow. Renaming a device in source does not enable it in Studio.

K: Invalid colour

Cause: A display control receives an unsupported value.

Example: BORDER 8 or BRIGHT 3.

Recovery: Use ordinary colours 0–7 and binary bright/flash states in tutorials. Special preserve/contrast values are command-specific.

L: BREAK into program

Cause: The programme was interrupted between statements.

Example: Using the emulated machine’s BREAK action during a loop.

Recovery: Inspect the preceding statement and state. CONTINUE normally proceeds rather than repeating it; Run from saved source when testing a repair.

M: RAMTOP no good

Cause: CLEAR requests an unsuitable upper BASIC memory limit.

Example: Lowering RAMTOP into occupied runtime storage.

Recovery: Restore a valid limit and rerun. Let the native assembly loader reserve its documented code region; do not guess a spare address.

N: Statement lost

Cause: A saved continuation or control-flow target refers to a statement that no longer exists.

Example: Editing away a pending return or continuation point on the machine.

Recovery: Restart from the saved programme after structural edits. Do not rely on old in-memory loop or return state.

O: Invalid stream

Cause: The selected historical stream is invalid or unavailable.

Example: PRINT to an unprepared stream.

Recovery: Use the ordinary screen channel in managed examples. Check stream allocation and channel setup in a separate peripheral exercise.

P: FN without DEF

Cause: A function call has no corresponding definition.

Example: FN f(2) without a definition.

Recovery: Add the matching DEF FN definition and check its function name and result type.

Q: Parameter error

Cause: A historical FN call supplies an incompatible argument count or type.

Example: Calling a numeric function with a string argument.

Recovery: Match the number and types of arguments to the DEF FN declaration, including any $ string parameters.

R: Tape loading error

Cause: A historical tape block cannot be read or verified as required.

Example: Incomplete or mismatching tape data.

Recovery: For managed Run, check the exact ROM, fresh build and loading completion. Rebuild and restart; do not launch an old artefact after a failed build.

Build success with a runtime failure

The encoder can package a recognised statement whose full argument syntax is wrong. It does not run the ROM interpreter. Treat an on-screen error as useful evidence rather than expecting Build to reject every language mistake. Conversely, a source quote/character/memory diagnostic needs repair before running and must not fall back to stale media.

Exercise: change a valid array example’s last index to one beyond DIM, note the report and repair the bound. Then test zero iterations in its loop. Keep these deliberately failing edits local to the experiment; the complete examples shipped in the guide are expected-success programmes.

Spectrum text, colours and attributes

The Spectrum display combines a monochrome bitmap with one colour attribute for each eight-by-eight character cell. A cell chooses ink, paper, brightness and flash for all its pixels. Two independently coloured shapes inside the same cell cannot keep separate attributes; the visible conflict is commonly called colour clash. Plan small games around this grid before attempting arbitrary pixel movement.

Text coordinates and output state

PRINT AT row,column uses row zero at the top and column zero at the left. Use rows 0–21 and columns 0–31 for ordinary BASIC upper-screen output. The physical screen has 24 rows, but the lower area belongs to ROM input/reports. Do not mix these coordinates with PLOT’s bottom-up pixel coordinates.

Set BORDER, PAPER, INK, BRIGHT, FLASH, INVERSE and OVER explicitly when an example needs a predictable display. Permanent statements affect later output; temporary controls inside a PRINT list apply to that output. CLS clears using the current permanent screen attributes. A paper colour change alone does not repaint every existing cell.

10 BORDER 0: PAPER 0: INK 7
20 BRIGHT 0: FLASH 0: INVERSE 0: OVER 0: CLS
30 PRINT AT 3,4;INK 6;"YELLOW LABEL"
40 PRINT AT 5,4;BRIGHT 1;"BRIGHT WHITE"
50 PRINT AT 7,4;"SCORE: 120"
60 PRINT AT 7,11;"9  "
70 STOP

The labels occupy separate rows. The score update prints a 9 and two spaces to remove the old trailing digits. Without the spaces, changing 120 to 9 would leave misleading characters. A real game should clear a fixed field or pad its new text deliberately. The temporary ink on line 30 does not change the intended permanent white for later lines.

The byte is ink + 8*paper + 64*bright + 128*flash. White ink on blue paper with bright enabled is 7+8+64=79. Physical attribute addresses start at 22528 ($5800), with address 22528+32*row+column. Attributes are linear even though bitmap scanlines are not. ATTR(row,column) reads the combined byte; compare a masked or decoded field when asking about ink alone.

Characters, UDGs and recognition

PRINT uses the ROM character shapes; SCREEN$(row,column) tries to recognise a character from screen pixels. A drawn shape or modified glyph need not be recognisable. Keep programme state in variables instead of assuming every object can be reconstructed from screen text.

In a suitable 48K BASIC environment, USR with a graphic-letter string identifies user-defined graphic storage. Eight bytes describe one eight-row character, most significant bit at the left. Editing those bytes changes the glyph definition, not every already-drawn copy. Graphical source escapes are not supported, and later ROM modes differ in their UDG arrangements; use ordinary characters in the cross-model tutorials.

Diagnose invisible or damaged output

If text disappears, check equal ink/paper, a later CLS, overwritten attributes and the output row. If old score digits remain, check field clearing. If a moving shape recolours its neighbour, check cell sharing before blaming the emulator. If PRINT asks “scroll?”, a loop is repeatedly adding lines; update at fixed coordinates or reduce the output.

Exercise: calculate an attribute for yellow on red with normal brightness, print a marker at a known cell, then change only that cell’s attribute through POKE. Predict which existing pixels change colour and why no new character appears. Restore the screen with your initial state and CLS.

Spectrum pixel graphics

Start with BASIC’s graphics operations before calculating bitmap addresses yourself. PLOT establishes a point, DRAW moves relative to the current graphics position and CIRCLE describes a circle. All still share the Spectrum attribute grid, so a pixel is not an independent full-colour dot.

Coordinate systems

BASIC graphics use x from 0 to 255 and y from 0 to 175, with y increasing upwards. Text uses row,column with row increasing downwards. The physical bitmap is 256 by 192, but BASIC reserves the lower area for input and reports. Name variables x,y for graphics and row,column for text to keep conversions visible.

10 BORDER 0: PAPER 0: INK 7: CLS
20 PLOT 32,32
30 DRAW 80,0
40 DRAW 0,48
50 DRAW -80,0
60 DRAW 0,-48
70 CIRCLE 172,88,24
80 PRINT AT 1,2;"BOX AND CIRCLE"
90 STOP

Expected result: a rectangular outline and a separate circle, with a title above them. DRAW’s operands are displacements, not absolute destinations. The box returns to its start after four sides. Keeping the circle well away from the screen edge avoids a partial off-screen experiment obscuring the first lesson.

Angles and pixel tests

The optional third DRAW argument bends a line into an arc by an angle in radians. Plan the shape and bounds before experimenting; an arc can leave the screen even when its endpoints appear safe. POINT(x,y) reads a bitmap pixel state. It does not return a shape identifier, collision object or colour. For a game, compare coordinates and object state first, then draw that state.

Overprinting and erasing

OVER 1 combines drawn pixels with what is already present, allowing an identical shape drawn twice to restore its pixel pattern. It does not automatically restore attributes changed while drawing. OVER 0 gives ordinary plotting; INVERSE changes the treatment of drawn bits. Keep a saved background or redraw the affected area for reliable animation rather than assuming XOR solves every overlap.

10 BORDER 0: PAPER 0: INK 7: CLS
20 FOR x=16 TO 80 STEP 8
30 PLOT x,80
40 DRAW 0,16
50 NEXT x
60 PRINT AT 2,2;"NINE VERTICAL MARKS"
70 STOP

There are nine marks because the inclusive sequence is 16,24,…,80. Count the expected iterations before running. Change STEP to 4 and predict the new count. Do not use a fractional loop variable repeatedly added to itself when exact endpoints matter.

Animation budget and recovery

BASIC graphics are interpreted and can be slow. Keep a small bounded object, update only what changed and avoid a complete CLS every frame if flicker matters. PAUSE allows pacing but can end early on a key. A later assembly version should keep the same object-state model, not merely translate every PRINT into a guessed memory write.

For an out-of-range report, inspect both the current graphics position and the proposed displacement. A correct first line can make the second invalid by moving near an edge. Test the first and last positions of motion and include an exit key. Studio Stop remains the recovery route if a loop does not service input.

Spectrum keyboard input and timing

In the original Spectrum runtime, the separate native window or browser Game panel owns programme input. Its command field enters complete BASIC text; the screen accepts native keyword keys and game controls. With explicit MAME, its external window owns input. Clicking a code editor or Help search box does not send keys to the emulated Spectrum. First confirm focus using a simple INPUT prompt. A missing response may be a focus problem, a held key, an unfinished tape load or a programme loop; diagnose those separately.

Line input and single-key input

INPUT waits for an entered value; INPUT LINE reads a string as text. INKEY$ samples a character without waiting for Enter and can return the empty string. Decide whether you want one action per press or continuous movement while a key is held. A menu usually wants the former, while a movement control may want the latter.

10 PRINT "PRESS A KEY ONCE"
20 IF INKEY$<>"" THEN GO TO 20
30 LET k$=INKEY$
40 IF k$="" THEN GO TO 30
50 PRINT "YOU PRESSED ";k$
60 IF INKEY$<>"" THEN GO TO 60
70 PRINT "KEY RELEASED"
80 STOP

The initial loop waits for a previously held key to be released, the second waits for a new character and the last waits for release. Expected output is one captured character followed by KEY RELEASED, rather than hundreds of actions from one hold. Test both a short tap and a held letter. Modifier keys alone are not ordinary printable input.

Pacing

These supported Spectrum profiles are PAL. PAUSE 50 approximates one second if uninterrupted, and PAUSE 1 is a useful small yield in a BASIC loop. A key can shorten the pause; PAUSE 0 waits for a key. Do not use PAUSE as a guaranteed wall-clock deadline. A game should define its movement rate and test held-key behaviour explicitly.

The ROM maintains a three-byte frame counter at FRAMES beginning 23672 in the ordinary environment. Reading its bytes separately can straddle an update, and it wraps. A robust wider counter read needs a consistency strategy. Introductory examples use bounded pauses instead of presenting a racy three-PEEK expression as an exact timer.

Keyboard matrix and ports

The keyboard is scanned through the ULA’s port space; selected address lines choose rows and low input bits describe keys. A pressed key is active-low: zero indicates pressed. This differs from INKEY$, which interprets characters through the ROM. Multiple simultaneous keys, modifiers and ghosting require a matrix-aware design, not a string comparison alone.

A Z80 IN A,(C) uses the complete BC port address. BASIC IN takes a numeric port address. Do not substitute a RAM PEEK for an I/O read, or assume an immediate eight-bit port form ignores its high address byte. The row table below gives the baseline key order from input bit 0 to bit 4. The complete game uses INKEY$ so it remains simple and clearly bounded.

Clean exits

Give interactive loops a visible quit key and test it with the emulator focused. The machine’s BREAK action and Studio Stop are separate recovery mechanisms. A debugger session pauses instruction execution and therefore also prevents normal programme input processing while stopped. Do not diagnose a paused programme as a broken keyboard.

Exercise: turn the example into a two-option menu, normalising upper/lower-case letters by checking both forms. Add a release wait so the selected action runs once. Then deliberately remove it to observe key repeat, restore it and document which behaviour your interface is meant to provide.

Spectrum sound and short tunes

Begin with BEEP because it is available across the registered Spectrum models and needs no direct hardware manipulation. Verify that MAME has audio enabled and that the selected output device is audible. A successful TAP build and a running emulator process do not establish that a tone was heard.

Duration and pitch

BEEP takes duration in seconds and pitch in semitones relative to middle C. Pitch zero is middle C, seven is the fifth above and twelve is an octave above. Negative pitches go lower. Keep within the ordinary -60 to 69 range and use short, nonnegative durations. BEEP occupies BASIC while it plays, so a long tone also delays keyboard polling.

10 BORDER 0: PAPER 0: INK 7: CLS
20 PRINT "FOUR SHORT NOTES"
30 DATA 0,4,7,12
40 FOR n=1 TO 4
50 READ p
60 BEEP 0.15,p
70 PAUSE 2
80 NEXT n
90 PRINT "TUNE COMPLETE"
100 STOP

Expected result: four rising notes, then TUNE COMPLETE. The pitches form a simple major-chord pattern. The screen messages make the control flow observable even before audio is confirmed. They do not prove the audio itself; listen in the active emulator. If only three notes seem audible, shorten the pauses or repeat the test before changing the programme.

Compose with explicit data

Keep a tune’s note count, pitches and durations together. If using pairs of DATA values, READ a pitch and duration for every note and match the number of pairs to the loop count. RESTORE the tune’s first line before replaying. Do not use an invalid pitch as a rest; represent a rest as a separate pause path.

PAUSE is frame-based and can end early on a key. It is adequate for an introductory gap between tones, not a precision sequencer. A game that must continue moving while music plays needs a different timing architecture; adding longer BEEP statements to its main loop will make input feel sluggish.

Beeper hardware and register ownership

The ULA output port combines border and sound-related bits. An assembly routine toggling a sound bit must preserve the intended border and other output meanings. The beeper’s pitch depends on the timing of repeated transitions; interrupts and contended memory access can alter that timing. This guide does not present a short delay loop as a cycle-accurate sound driver.

Do not leave an unbounded port-toggling loop running without a stop path. Begin with a bounded routine and restore its output state before returning. Explicit MAME assembly Debug’s standalone snapshot lacks the BASIC ROM workspace and timing environment of Run; hearing a correct note is a real runtime observation, not a source-map assertion.

The original UK 128K and grey UK +2 runtime provides eight RAM banks, the alternate screen and AY sound without external setup. The same guest BASIC implements PLAY, SPECTRUM and the RAM disc. SAVE! and LOAD! accept programme, CODE, SCREEN$ and DATA files; MERGE! merges BASIC, CAT! lists names and ERASE! removes a file. NEW keeps the disc; Reset clears it. There are 32 entries and 80,896 payload bytes. Replacement needs room to stage the new file. Banked object linking and external MIDI/serial peripherals are not implemented. +2A/+2B/+3 are separate machines.

128K and original +2 sound

The UK 128K and original grey +2 add an AY sound chip with three tone channels, noise, a mixer, channel amplitudes and an envelope generator. In 128 BASIC, PLAY provides a higher-level music-string interface. The source encoder recognises PLAY only for those two registered profiles. Its presence is not a claim that every ROM mode or music string has been exercised by Studio’s tests.

The AY uses a register-selection port and a separate data port. Tone period uses paired register fields, the mixer combines enable bits and envelope state can affect amplitude. Treat any direct driver as model-specific and preserve unrelated channel settings. The baseline tutorial stays with BEEP; use the original 128 manual for PLAY’s full string grammar and validate it in the chosen model before relying on it.

AY register map for the 128K models

The standard register-selection port is $FFFD (65533), and the data-write port is $BFFD (49149). Select a register before writing its data; a read of the selection/read port retrieves the selected register where supported. These ports are not available as AY hardware on a stock 16K/48K. A driver must preserve the machine’s other uses and silence or restore the channels it owns on exit.

Change the data to a descending sequence and predict which note is first. Add a fifth note and update the count; leaving the count at four is a useful example of valid code with an incomplete result. Bitmap addressing

For a physical top-down pixel coordinate x=0–255, y=0–191, the bitmap byte address is 16384 + 2048*INT(y/64) + 256*(y modulo 8) + 32*(INT(y/8) modulo 8) + INT(x/8). The bit mask is 128 shifted right by x modulo 8. “Modulo” and “shift” here describe the calculation; they are not proposed Spectrum BASIC keywords.

For example x=0,y=0 uses 16384; x=0,y=1 uses 16640, not 16416. Adding 32 reaches the next character row’s corresponding scanline within a third of the display, not generally the next physical pixel row. This distinction explains many striped or scrambled graphics bugs. Test a single byte and a single character cell before implementing a screen-wide routine.

The matching attribute address is 22528+32*INT(y/8)+INT(x/8). All eight scanlines in the same character cell use that one attribute. BASIC graphics coordinates reverse y and expose only the upper drawing region, so do not insert a BASIC PLOT y directly into the physical top-down formula.

System pointers are live state

Useful baseline names include PROG at 23635, VARS at 23627, FRAMES at 23672 and RAMTOP at 23730. PROG, VARS and RAMTOP are two-byte little-endian fields; FRAMES is three bytes. These names document memory locations and are not predefined BASIC variables you can print by name.

Read-only inspection is a good first exercise; blindly changing a pointer can break the interpreter. A byte sequence beginning at a remembered BASIC variable address may move after allocation. Avoid storing raw pointers to movable BASIC strings across operations that can reorganise workspace.

Assembly storage and return

Studio’s native loader clears below the fixed code origin, loads CODE and calls USR 24576. A single assembly image includes its instructions, DB/DW tables and DS reservations. Reserve private buffers inside that image, with RET before data so execution cannot fall through. Do not overwrite your own code or the active stack with a convenient-looking POKE.

On a 48K Spectrum, screen RAM and other lower RAM accesses can be contended by display activity. Instruction timing tables describe CPU work but do not alone predict every machine-level delay. Timing-critical raster or audio work requires a deliberately chosen model and observed runtime tests; it is outside the beginner projects and not proved by ordinary build tests.

Inspect and recover

Start with an attribute byte whose effect is visible and reversible by CLS. In assembly Debug, inspect a private data label and its bounded range. Stop before editing source; stale maps cannot identify a new build’s instructions. If a bad memory write crashes the ROM, Studio Stop and a fresh Run restore a new managed machine; saved source remains the place to repair the bug.

Spectrum ROM calls and assembly return

A ROM address is an entry into code that expects a particular machine state. It is not a self-contained library function simply because the address is small. The selected ROM, active channel, system variables, stack and registers can all be part of its contract. Start with direct private-memory routines before depending on the interpreter.

The managed caller

For Run, Studio packages a BASIC loader that reserves the assembly region, loads the code block and invokes RANDOMIZE USR 24576. USR creates a machine-code call context; a normal RET returns through that context. The numeric USR result is associated with BC. A routine used for its display side effects need not invent a result, but it must preserve the return structure.

Preserve IY for ordinary Spectrum ROM use and do not casually repurpose the alternate register banks. Balance every PUSH/POP, restore any state your contract promises and avoid replacing SP. If you call a subroutine that clobbers HL, save a live string pointer around that call or choose a different documented ownership scheme.

A small output call, for Run only

    ORG 24576
    PUSH IY
    LD A,83
    RST 16
    LD A,13
    RST 16
    POP IY
    RET

In the ordinary Spectrum 48K Run environment, this is intended to print S followed by a newline through the current output channel. RST 16 is RST $10, a fixed vector; it pushes a return address just like a short call. A holds the character/control code on entry. Treat the call’s working registers and flags as clobbered unless the specific ROM contract says otherwise. This example deliberately has no live pointer or loop counter across the call.

Expected observation is a letter and newline in the external emulator, followed by a safe return to the loader. Encoding and assembly tests do not establish that observation. Test this ROM-dependent listing with Run on the named target, not as a general cross-model or standalone-snapshot promise.

Why Debug is different

Explicit MAME Spectrum 48K assembly Debug starts a standalone snapshot with zero-filled RAM and code at $6000. It does not initialise BASIC workspace or create a BASIC caller. A ROM print routine may therefore fail even though it works from Run. A top-level RET also has no BASIC return to resume. Stop at the end of the routine before stepping that RET in Debug.

Use the Attribute banner project for source stepping because its body writes a fixed display region without ROM calls. Use private data buffers for arithmetic exercises. Registers, memory and source highlighting are meaningful only while stopped. Unsupported targets do not acquire a debugger by changing a Help example.

Error exits and interrupts

A ROM error path can unwind through interpreter state; it is not always an ordinary RET to your next instruction. Do not call a parser or calculator entry without understanding its stack and error conventions. RST $08 is not a generic printable error function. Changing interrupt mode or leaving interrupts disabled can break ROM keyboard and timing behaviour after your routine returns.

A register saved for an output result must not be overwritten by your cleanup. If you promise BC as a numeric result, do not restore the caller’s BC over it. If the routine is used only for side effects, document that its result is ignored. These small decisions make the difference between a reproducible example and one that works accidentally under one register state.

Practical checklist

Identify the exact ROM mode; state input registers and channel requirements; list clobbers; ensure a balanced stack; define a normal and failure exit; test repeated calls. Keep original ROM bytes outside source control. This guide uses documented interfaces and original examples and does not ship recovered ROM implementation code.

How the state works

r,c are the player row and column; sr,sc are the target position; s is the score and k$ the sampled key. The legal play area is rows 4–18 and columns 1–30. Lines 170–200 clamp movement before any updated position is drawn. The target generator excludes the player’s current cell, so collecting does not immediately create another target underneath the player.

Line 120 erases the old player. Lines 130–160 change its proposed position, and line 210 tests the logical coordinates rather than decoding the screen. The drawing routine prints the target, player and score. A fixed seed makes the placement sequence repeatable when following the same collection path. The random routine’s retry is expected to finish quickly but is not a hard real-time bound.

The control descriptions are above the playfield. STOP at both exit paths prevents execution falling into line 500. The drawing and placement routines return to their caller and share the main programme’s variables deliberately. PAUSE 2 supplies simple pacing, though a held key can shorten it; movement is intentionally repeatable while held.

Expected results and checks

On first display there should be one player and one yellow target, with score zero. Press each movement key and verify its direction. Hold the keys at every edge: no Out of screen report should appear and the player must stay in the play area. Collect one target and verify exactly one score increment, one short tone and a newly placed target. Collect five to see the completion message; press X in a separate run to test early exit.

Build success establishes source encoding and tape packaging, not those input, visual or audio observations. If the player does not move, check MAME focus and tape completion first. If old characters remain, inspect erase/draw order. If the score rises incorrectly, inspect coordinate equality and target replacement. Bounded extensions

Change the goal to three and update both the title and completion condition. Add a move counter initialised at startup and updated only when the position actually changes. Then add one fixed obstacle: test the proposed position before committing it, rather than drawing into the obstacle and hoping colour clash detects it.

For one-step-per-key movement, add a release-wait phase as in Keyboard input. Keep the exit key working in every input state. Spectrum assembly project: an attribute banner

This original project draws a horizontal colour banner by replacing one row of screen attributes. It uses no ROM output routine, so its body is suitable for inspection in Spectrum 48K Debug as well as ordinary Run. Its normal RET returns to the Run loader’s BASIC caller. Why the pixels do not need clearing

The destination is 22528+5*32=22688, the first attribute in physical character row five. There are exactly 32 bytes, one per column. Each value is colour+8*colour, so ink and paper are identical. Existing zero and one bitmap pixels therefore both show the same colour within the cell. The visible result is four repetitions of blue, red, magenta, green, cyan, yellow, white and black.

This is an attribute banner rather than a text-string banner; it demonstrates the separation of bitmap and colour storage. The routine copies no bitmap bytes and does not pretend to create independent coloured pixels. Bright and flash are off in every table value. Run’s ROM may change other screen areas when the routine returns, but it need not overwrite row five to show its report.

Register and memory contract

HL is the source pointer, DE the destination and BC the nonzero byte count. LDIR changes all three, so the programme saves and restores them. It leaves IY and alternate banks alone and uses a balanced stack. AF is not promised preserved. The private table lies after RET so it cannot become the next executed instruction during a normal call.

The output region is exactly 22688–22719. The image contains only its short instruction sequence and 32 data bytes, well below the 8192-byte limit. Increasing BC without extending the table would read unrelated memory. Moving the destination down by 32 would select the next attribute row; moving it by one would shift the operation across a row boundary.

Run acceptance

Run a fresh build, wait for tape loading and inspect the external emulator. The intended observation is the repeated colour row, followed by a safe return to the BASIC loader. Repeat Run and verify the same result rather than relying on a previous screen. Assembly success alone proves neither the visible colours nor that a real machine would behave identically.

Debug acceptance

Use Debug (F5) on Spectrum 48K. At the entry stop, inspect the instruction and SP. Set a source breakpoint on NOP after finished, using the emitting NOP line rather than the label-only line. Continue there and inspect 32 bytes at $58A0: they should match the four eight-byte rows in the listing, and BC should be zero before the saved value is restored.

Step the POP instructions and confirm SP returns to its entry value. Stop before the final RET. This verifies the body and stack balance without pretending the standalone snapshot has a BASIC return address. Do not call ROM print helpers to display the result inside Debug. Stop before editing, then rebuild so source maps remain tied to the current image.

Exercises and recovery

Change the destination to row six by adding 32 and predict the new position. Then enable bright by adding 64 to selected table values. For a new pattern, keep the 32-byte length unchanged initially. Test that only the intended row changes. If the debugger reports a stale map or modified code, stop and rebuild; never patch instructions while expecting old source breakpoints to remain authoritative.
