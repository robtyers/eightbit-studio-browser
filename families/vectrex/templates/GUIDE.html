The project includes no firmware or commercial game; Studio supplies an original development runtime and executive.

Create, build and run

Use Eightbit Studio 6809 for Vectrex development. The standalone macOS Vectrex compatibility wrapper is retained for compatibility testing; it has separate settings and credentials, with LWTOOLS and runtime selections together under Application Settings → Emulator.

  1. Choose File → New Project. Select Target machine → Vectrex, then Vector, sound and controls. Choose a parent folder and a new child-folder name. The location picker starts in your home folder. Existing destinations are rejected intact.
  2. The opening screen contains project actions and recent projects. Inside the IDE, an empty editor displays the studio processor mark. Open src/asm/main.asm. New projects include README.md, AGENTS.md, CLAUDE.md, .gitignore, this GUIDE.html and tests/README.md. Opening remains offline and inert.
  3. In Application Settings → Build Tools, select a separately installed LWTOOLS 4.25 folder containing both lwasm and lwlink. Select Validate and save. The cartridge uses raw assembly; the current tool adapter still validates the pair.
  4. Save, then select Build. Inspect Build Results and Output. Success publishes .vectrex/build/cartridge.bin, cartridge.lst, symbols.txt and manifest.json. Nothing starts automatically.
  5. For this starter, choose Run original (development) in Emulator. No external tools or third-party firmware are required. Focus the shared screen: arrows move, Z/X/C/V are buttons 1–4. Browser Play uses the same original runtime. Its executive is a documented development subset; music and unlisted BIOS services fail explicitly. Keep VecX for compatibility checks.
  6. For external playback, install and select RetroArch and its VecX core using the setup steps below, then validate and save in Application Settings → Emulators → Vectrex.
  7. Select Run Project. Saved source is freshly built before an external emulator window opens. Focus that window. Directional controls move the diamond; Vectrex button 1 controls a tone.
  8. Use Stop beside Run Project to end the session. Restart in Emulator stops, rebuilds and starts again. A failed build never launches the previous successful cartridge.

Install and locate LWTOOLS

Default Build uses the original built-in 6809 assembler. Build with LWTOOLS is the explicit compatibility action and requires LWTOOLS 4.25. The Build Tools selection is shared with Dragon projects. For a Homebrew installation, with Homebrew installed, enter these commands yourself in Terminal:

brew install lwtools
lwasm --version
lwlink --version
brew --prefix

The Homebrew LWTOOLS formula supplies both tools. Check that both report 4.25; a future formula update may install a version this Studio release does not accept. Select the bin folder beneath the Homebrew prefix, normally /opt/homebrew/bin on Apple Silicon or /usr/local/bin on Intel. Choose the folder containing both executables, not an individual file. For a custom installation, use its actual tool folder. Select Validate and save; if validation fails, check both versions and the selected folder before retrying.

Using Vectrex and the emulator

Vectrex is a cartridge console with a built-in monochrome vector display, sound and two controller ports. It has no Dragon-style BASIC prompt, keyboard command language or cassette workflow. A cartridge begins through the machine's executive startup; your program maintains its own frame loop. Coloured overlays are physical artwork rather than pixel colours generated by the CPU.

For an original console, follow its owner's instructions: switch off before changing cartridges, connect the controller, insert a compatible cartridge, then switch on and adjust normal user controls. This guide does not provide CRT servicing instructions. The IDE's Run action operates an emulator and does not program a flash cartridge.

The original development executive supports the starter's Wait_Recal, direct-page setup, Read_Btns, Joy_Digital, Sound_Byte, intensity, Moveto_d, Reset0Ref and Draw_Line_d calls. Development profile 0.2 also supports single-string text ($F373/$F378/$F37A/$F495) with an independently drawn font, plus counted draw/move lists ($F3AD–$F3DF at the published entries). Text is limited to 256 characters in $20–$6F followed by $80. Development profile 0.3 adds packet lists ($F404/$F408/$F40C/$F40E/$F410): signed mode,Y,X triples, $00 blank move, $FF solid draw, $01 terminator, up to 256 vectors. X returns on the terminator; invalid modes or address wrapping fault. Development profile 0.4 adds TXTSIZ ($F385) and TXTPOS ($F38C) text lists: up to 64 messages of 256 characters, with a leading zero byte ending the list. U returns after that final zero; only published text size/pointer RAM changes. Empty lists are valid and pointer wrapping faults. Development profile 0.5 adds DSHDF ($F434), DASHDF ($F437) and DASHPK ($F46E): DASH/$C829 supplies the pattern; counted lists have 1–256 pairs, and patterned packets have up to 256 vectors with $00 blank, $02 solid, $FF patterned and $01 terminator. X returns after the final pair or packet terminator. Malformed modes, counts or wrapping fault; non-zero ZSKIP zeros after the list. Patterns use the original VIA shift model, not qualified historical phase/timing. The optional pattern-demo.asm exercises all three calls. $F38A, $F433/$F439, grid lists and music remain unavailable. Other services described below are reference contracts for compatibility development and may require VecX; they are not implemented merely because the guide describes them. The display uses idealised vectors rather than analogue/CRT simulation. No debugger or historical-game qualification is included.

RetroArch supplies video, audio and input outside the IDE. Check its current input mapping for Vectrex button numbers and directional controls; do not assume a Mac key labelled “1” means button 1. The starter uses digital direction signs. Analogue sensitivity and physical-controller behaviour require separate observation. VecX documentation says no separate BIOS file is required; this says nothing about rights to redistribute firmware or games. See the core's operating reference.

The IDE uses private configuration, cartridge, save, state and system directories, with online emulator features disabled. It does not inherit your ordinary RetroArch configuration; input changes made in an IDE session may need repeating next session. Stop/Restart replace the owned process and temporary state, so do not rely on emulator save states being retained. The session has a 12-hour safety limit. “Running” means a process is alive; confirm the picture, sound and controls yourself.

Project files and source control

schema_version = 1
name = "My vector cartridge"
target = "vectrex"
source = "src/asm/main.asm"

vectrex.toml accepts exactly these four fields. Names are non-empty, at most 80 UTF-8 bytes and contain no control characters. The single source must be a lowercase .asm path under src/, at most 128 KiB, without symlinks or path escape. The manifest is limited to 8 KiB. Do not add dragon.toml to this folder: two recognised manifests make the target ambiguous.

The current Explorer edits the configured source only. The supporting files are also listed in Explorer: select one to reveal it in Finder, then open it in your preferred text editor, or open this standalone guide in a browser. Open Project in Finder reveals the whole project folder. Reopen after externally changing the manifest. A source changed on disk causes stale-save rejection; preserve your unsaved work before reloading.

Use README.md for onboarding and AGENTS.md for coding conventions. Update tests/README.md alongside changes. None of these files executes commands or grants AI authority. The optional AI Agent uses the shared Studio provider settings, context preview and guarded editing workflow below. Existing projects open without new files being inserted; template updates apply only to newly created folders.

Machine and memory map

RegionPurposeProgramming rule
$0000–$7FFFUp to 32 KiB unbanked cartridgeHeader, executable code and immutable tables; do not store mutable variables here.
$C800–$CBFF1 KiB physical RAMShared by executive workspace, game state and stack; not all available to your variables.
$D000–$D00F6522 VIA registersTiming and analogue hardware; avoid casual writes while using BIOS services.
$E000–$FFFFExecutive ROMCall documented services; do not embed ROM bytes.

These are the useful base regions, not an exhaustive decoding/mirroring map. Consult the original programmer's manual for hardware detail.

The starter allocates X_POS, Y_POS and TICK at $C880–$C882 with EQU. Plan later variables explicitly and retain stack headroom at the top of RAM. EQU names an address; it neither emits storage nor clears RAM. Initialise every game variable before use. Keep BIOS scratch locations out of your persistent state.

The 6809 hardware stack grows downwards. Nested calls and saved registers consume it. Avoid recursion, unbalanced pushes/pulls and large temporary buffers. Record a simple RAM allocation table in your source before adding objects; overlapping an object array with the stack can look like a random drawing or return-address bug.

6809 programming foundations

A and B are 8-bit accumulators; together they form D, with A as the high byte. X/Y are 16-bit index registers, S the hardware stack and U a second pointer/stack. PC tracks execution; DP supplies the high byte for direct addressing. CC holds flags, including zero, negative, carry and signed overflow. Words are big-endian. See the Motorola programming model.

; Fragments to place within a program, not whole cartridges:
        lda     #$18        ; Immediate: the value 24.
        sta     >$C880      ; Extended: store at this absolute RAM address.
        ldx     #$C880      ; X receives an address.
        ldb     ,x          ; Indexed: read the byte at X.
        ldd     #$1818      ; A=24 (Y), B=24 (X) for a vector call.

The # is significant: LDA #$18 loads a number, whereas LDA $18 reads memory. Prefix > forces an extended address in LWASM. Indexed forms include ,X, 2,X, ,X+ and ,X++; choose the increment to match byte or word data. A bracketed indexed operand adds indirection through a pointer.

SETDP $C8 only tells the assembler what to assume. Changing the CPU requires code such as LDA #$C8 then TFR A,DP. BIOS calls often require $D0 instead; Wait_Recal establishes that page. An incorrect direct-page assumption can redirect an otherwise valid store. Use extended addresses for game RAM while learning.

Separate calculation, comparison and branching. After CMPA #limit, use signed branches for signed positions and unsigned branches for byte counts. Test $7F/$80 boundaries. Declare each helper's inputs, output, clobbered registers and stack use; reload BIOS arguments immediately before calling. Do not assume A, B or X survives a BIOS call.

Instruction and directive reference

This working reference groups the 6809 instructions admitted by the Vectrex source validator. Each instruction has its own valid operands and flag effects; use the Motorola instruction entries for encoding and cycle detail.

ArithmeticADDA ADDB ADDD ADCA ADCB SUBA SUBB SUBD SBCA SBCB; CMPA CMPB CMPD CMPX CMPY CMPU CMPS; INC INCA INCB DEC DECA DECB; NEG NEGA NEGB; MUL SEX DAA.
LogicANDA ANDB ORA ORB EORA EORB BITA BITB; COM COMA COMB CLR CLRA CLRB TST TSTA TSTB; ANDCC ORCC.

ControlJMP JSR RTS BSR LBSR BRA LBRA BRN LBRN NOP; RTI SWI SWI2 SWI3 CWAI SYNC. Interrupt/wait instructions need a deliberately designed system context.
ConditionsBEQ/BNE for equality; BMI/BPL for sign; BCS/BCC (BLO/BHS aliases) and BHI/BLS for unsigned comparisons; BLT/BGE and BGT/BLE for signed comparisons; BVS/BVC for overflow. Long conditional forms add L, such as LBEQ.

JSR/BSR save a return address; RTS returns. Pair pushes and pulls. BRA repeats without growing the stack. Short branches have limited displacement; use the matching long form when code growth puts a destination out of reach. Compare flags must be consumed before intervening instructions change them.

DirectiveUse in this target
ORGExactly once, at 0 ($0 or $0000 also accepted). No later RAM origin.
EQUName constant values or RAM addresses without emitting bytes.
FCB / FDBEmit bytes / big-endian words into the cartridge.

Use colon-suffixed labels, indentation for instructions and semicolon comments. The source boundary rejects includes, INCBIN, macros, pragmas, sections, external linking and allocation directives such as RMB, even if LWASM itself supports them. Keep code and data in one file and allocate mutable RAM with EQU.

Cartridge header and first program

Keep the starter header until you have a working frame loop. Its fields are the recognised g GCE prefix and text ending with $80, a music address word, four title-layout bytes, one title ending with $80, and a zero ending the title list. Executable code follows. The $FD0D word refers to an executive tune; it is an address, not copied music or BIOS bytes. Header recognition is a format convention, not a licence grant.

This original complete example draws one short horizontal segment. Try it in a separate new project by replacing its source; keep the original demo in your first project. A successful assembly is only the first check—observe the line in your emulator.

        org     0
        fcc     "g GCE 2026"
        fcb     $80
        fdb     $FD0D
        fcb     $F8,$50,$20,$C0
        fcc     "FIRST VECTOR"
        fcb     $80,0
frame:  jsr     $F192
        jsr     $F2A9
        jsr     $F354
        lda     #$60
        sta     >$D004
        clr     >$C823
        ldd     #$0040
        jsr     $F3DF
        bra     frame

The supported validator accepts a 20–32768-byte cartridge, a copyright/header terminator within its initial 40 bytes, four title-layout bytes, one title terminated within 80 bytes, then zero and at least one code byte. It does not prove that pointers, opcodes or game logic are correct. Keep branch targets out of header and data bytes.

Frames, vectors and text

A useful frame structure is: Wait_Recal → read input → update state → draw objects → update sound → branch back. Wait_Recal waits for the refresh timer and recalibrates the beam reference, leaving DP=$D0 and changing D/X. Call it once per frame; do not carry unsaved register values across it. See Wait_Recal's contract.

Every visible object must be redrawn. Start modestly: excessive vector work per frame can reduce refresh stability. Keep gameplay loops bounded and avoid busy-wait delays for animation; use a frame counter. Separate persistent game positions from temporary drawing arguments.

Reset0Ref establishes the origin. Set brightness and vector scale, then move with the beam blanked before drawing. For Moveto_d, A is signed Y and B signed X; establish the origin first when treating this as an object position. The routine changes D. See Moveto_d.

Draw_Line_d uses relative signed Y/X displacements at the current scale and requires DP=$D0 and $C823=0 for one vector. It changes D and advances X by two. Reload each segment's arguments. See Draw_Line_d. The demo's four pairs (24,24), (-24,24), (-24,-24), (24,-24) close a diamond. Larger scale or coordinates change its size; these are analogue vector units, not screen pixels.

For a second object, reset/reposition independently instead of relying on the previous endpoint. For text, Print_Str_d at $F37A takes a string pointer in U and Y/X in A/B; use the documented high-bit terminator and text-size workspace conventions. Text costs frame time, so begin with one short label. See Print_Str_d for its inputs and clobbers. Do not substitute Dragon character-screen routines. Consult the BIOS reference before adopting vector-list formats: different routines interpret counts and terminators differently.

Controllers and buttons

The starter sets $C81F=1 and $C820=3 to sample controller 1 horizontal/vertical axes, and clears $C821/$C822. Joy_Digital ($F1F8) writes corresponding values at $C81B/$C81C: negative for left/down, zero for neutral, positive for right/up. DP must be $D0; D/X are changed. Joy_Analog ($F1F5) is a distinct service needing resolution setup and controller acceptance. See joystick inputs.

Read_Btns ($F1BA) updates held-button bits at $C80F and press-transition bits at $C811. Controller 1 buttons 1–4 occupy masks $01/$02/$04/$08; controller 2 uses the upper four bits. Read once per frame. Use held state for continuous sound/movement, transitions for one-shot fire/menu actions. Its A result is the transition state; B/X change. See button-state contracts.

; After Read_Btns; fragment for a one-shot button-1 action:
        lda     >$C811
        bita    #1
        beq     no_press
        inc     >$C882
no_press:

Keep this exercise separate from the demo's automatic TICK increment. First predict the result: holding the button should increment only once; releasing and pressing again should increment again. Verify neutral, diagonals, repeated presses and release. The starter's positions are signed bytes and wrap; a game may instead clamp them before increment/decrement. Choose that policy explicitly and test all four boundaries.

Sound programming

The demo writes channel A's fine/coarse period with Sound_Byte ($F256), then the mixer and volume. A selects the PSG register; B supplies its value; DP must be $D0. The routine updates the executive shadow and changes D/X. Reload both arguments each time. See Sound_Byte.

Demo writeMeaning
Register 0 ← $A0; register 1 ← $01Channel A tone period $1A0. Adjust the period to experiment with pitch.
Register 7 ← $3EEnable tone A and disable other tone/noise channels, retaining the demo's I/O-direction setting.
Register 8 ← 8 or 0Fixed channel A volume while button 1 is held; silence on release.

These values come from the checked-in original demo. Extend them one change at a time: replace $A0 with another fine period, save/build/run and compare the audible result at a comfortable host volume. Do not reuse sound-chip registers as generic variables or alter mixer I/O bits casually, because controller reads share the hardware interface.

For a bounded sound effect, add a duration counter to your RAM allocation and decrement it once per frame. Select the period/volume while the counter is non-zero and explicitly write silence when it expires. Test retriggering, release and state changes. Keep a simple direct-tone approach until you deliberately adopt the BIOS music-buffer/Do_Sound contract; mixing both approaches without ownership of the sound state can overwrite your changes.

Understand and extend the demo

  1. Header: ORG 0 and the single title precede start. Change the title text conservatively while retaining its terminators.
  2. Initial state: X_POS, Y_POS and TICK are cleared; controller 1 axes are enabled. These are RAM addresses, not cartridge storage.
  3. Frame: Wait_Recal, Read_Btns and Joy_Digital establish timing and current input. Horizontal and vertical branches independently alter position.
  4. Diamond: drawing starts from a reset reference, sets scale $60, moves to Y_POS/X_POS and draws four relative segments.
  5. Moving line: a second reset makes it independent. TICK & $3F then subtracting $20 supplies its repeating vertical offset. It continues moving while the joystick is neutral.
  6. Tone: period/mixer writes are followed by a volume selected from held button 1. LBRA returns to the frame without adding a stack entry.

Build a learning sequence in separate source revisions:

  • Geometry: halve all four diamond displacement pairs. Predict closure and size; check that independent line motion stays unchanged.
  • Movement: clamp X/Y to chosen signed limits before each increment/decrement. Hold at every boundary, release and move back. Include corners.
  • Input: assign a spare button's transition bit to reset the position. Holding must not repeatedly trigger if you selected one-shot behaviour.
  • Sound: use a short countdown effect instead of continuous held sound. Verify expiry, retriggering and silence after Restart.
  • Game structure: add title/play/game-over state bytes, a bounded object list and explicit collision rules. Keep update logic independent of drawing and record the RAM/stack budget.

These are exercises, not implemented starter features or claims of tested gameplay. Add expected outcomes to tests/README.md before changing code. Do not add a second assembly file: use labelled helpers and tables inside the configured source.

Testing, export and hardware

Use the generated tests/README.md as a repeatable checklist. No Vectrex Test Explorer schema or source-level debugger is implemented. Do not add Dragon .dragon-test.toml files or treat listing/symbol output as an integrated debug map.

First check Build: syntax accepted, cartridge header valid, output within 32 KiB, stable SHA-256 for identical source/tools. Inspect cartridge.lst for instruction addresses and symbols.txt for labels. A symbol with a valid address can still point at the wrong logic. Then check runtime separately: visible geometry, refresh, all input directions, held/transition buttons, sound/silence and Restart/Stop recovery.

For a regression, record the original failure, exact change, expected result and steps that distinguish fixed behaviour from the previous version. Exercise invalid source in a disposable copy and verify no old cartridge runs. Cancel an operation where possible and retry successfully. Record unperformed checks as pending, with source/tool/core versions; do not include sensitive paths or payloads.

After a successful current Build, choose Export cartridge in Build Results. Select a new filename: the exporter rejects existing destinations and changed source/output. Keep the exported binary's hash, size and source revision in your release notes. Export is a local file operation and does not publish or transfer anything to hardware.

Physical Vectrex acceptance needs separately provisioned, compatible hardware and a flash-cartridge-specific procedure approved by its owner. Emulator success does not establish timing, analogue behaviour, display calibration or physical safety. Bank switching, specialised peripherals, calibrated overlays and a physical deployment pipeline are outside this target's implemented contract.

Troubleshooting and supported limits

Symptom / codeWhat to check and how to recover
DSV1000 — project configurationUse the four schema-1 fields, target vectrex and one src/*.asm source. Remove foreign/unknown manifest fields; do not convert a Dragon project in place.
DSV1001 — file operationCheck the selected parent is writable and the destination new. Preserve existing files and retry with another folder/name.
DSV1002 — bounds/pathUse regular files without symlinks, paths within the project and supported file sizes.
DSV1003 — stale sourceSource or manifest changed externally. Preserve unsaved text, reopen and reconcile before saving again.
DSV1100 — source contractCheck ASCII, line length, one ORG 0 and allowed instructions/directives. Remove includes, macros and reservations.
DSV1101 — cartridge headerRestore the starter header layout and terminators, with code following the single title and total size within 32768 bytes.
DSV1102 — build process/toolValidate LWTOOLS 4.25 and both executables. Cancellation, timeout or excess output also stops a build; correct the cause and retry.
DSV1103 — assemblyCheck the reported source lines, label spelling, operands and branch range. Save corrections and build again.
DSV1200 / DSV1201 — runtime setup/sessionCheck selected executable/core and operation state; stop an owned session if necessary, correct setup and retry. Read the accompanying bounded message.
DSV1104 — build publication/freshnessCheck output-directory access and rebuild current saved source; publication failed or source/output no longer matches the selected result.
Process runs but screen is blankFocus/check the external window and core. Revert to the starter, then inspect header, frame loop, DP, intensity, scale and coordinate order. Process state is not rendering evidence.
Distorted vectors or crashesCheck Wait_Recal, $C823 before single lines, independent object origins, register clobbers, signed overflow and stack/RAM overlap. Reduce to one object.
No input or soundCheck external-window focus and current input mapping, channel-enable bytes, held/transition choice, host mute, PSG mixer and volume. Use the original demo as a baseline.

Current limits: one source; up to 32 KiB unbanked cartridge; no BASIC, includes, macros, multi-object linking, Vectrex debugger. Tools and emulator remain separate installs. Success in ordinary mock tests, a real assembler, an external emulator, a packaged app and a physical console are distinct evidence layers.

References and provenance

This guide, checklist and examples are independently written Apache-2.0 material. Technical references supply hardware, file-format and API facts only; no recovered BIOS implementation, commercial game, firmware bytes, emulator code, original diagrams or manual listings are reproduced. External resources are optional, explicitly opened links; the guide itself works offline.

  • Vectrex programmer's manual, volume I — original hardware and executive documentation.
  • Motorola MC6809/MC6809E programming manual and instruction appendix — archived primary CPU documentation.
  • Vectrex BIOS API catalogue — call addresses; use the individual contract links in the programming sections. Do not follow implementation listings as a source of shipped code.
  • LWTOOLS manual — assembler syntax; the IDE intentionally accepts a narrower single-source subset.
  • Libretro VecX documentation — core setup, controls and BIOS requirements.
  • RetroArch command-line documentation — external core/content selection; IDE invocation remains fixed and supervised.

The template source and native project/build contracts are authoritative for what this application implements. References to broader machine capabilities do not enable additional IDE features. Record actual emulator and hardware results separately from the guide's examples.

External emulator window

Run opens the emulator in its own window and leaves your source editor visible. Use the Emulator panel for Run, Stop and Restart. Keyboard, controller input and audio stay with the external emulator. There are no embedded display or Split controls.

Rebuild on save defaults on after a project Run. Saving source builds and restarts the cartridge, resetting programme state. Turn off Rebuild on save in the Emulator panel to keep the current run. External cartridges, project opening, AI source writes and close-time saves do not auto-run. A failed build never launches old output.
