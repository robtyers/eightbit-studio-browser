Getting started

Choose New Project, a supported machine, and its BASIC or 6502 assembly template. The tutorial in this article uses Commodore 64 (PAL) and Commodore BASIC V2; for BBC projects choose the BBC Model B machine guide. Choose a new folder name, then Create. Opening and creating projects never starts an emulator.

Edit src/basic/main.bas or src/asm/main.asm, Save, then Build. BASIC builds work offline without tools or firmware. Export PRG writes a new file; Run builds again and starts your separately configured VICE installation. A failed build never launches an older programme.

The 6510 in the C64 executes the NMOS 6502 instruction set. Other Commodore machines, NTSC targets, 65C02 and 65816 are not registered in this release.

Choose a learning path

If you are new to programming, start with Using the C64, then Commodore BASIC V2, Decisions, loops and subroutines, and Strings, arrays and data. Type the small examples into a BASIC project one at a time. Finish with the keyboard-game tutorial, which combines those techniques into one complete programme. Keep the language and error references open when an unfamiliar command or message appears.

If you already write BASIC, try the screen, sprite and sound articles. They explain the C64 hardware addresses used by the examples instead of treating POKE numbers as magic. The memory-map article helps you understand which locations belong to the programme, the operating system and the display.

For assembly, read the processor model, addressing modes and instruction reference before C64 assembly projects. Continue with arithmetic and common programming patterns, then build the assembly text-banner project. The first-party examples use the supported single-source ca65 subset and the same fixed entry point as a new Studio project.

A repeatable first run

Create a BASIC project and replace src/basic/main.bas with the complete example below. Save it, choose Build, and inspect the Build panel. A successful build produces a PRG. You can develop and export BASIC without installing an assembler. To observe its output, configure VICE and the C64 firmware in Settings, then choose Run and bring the VICE window forward.

10 PRINT CHR$(147)
20 PRINT "MY FIRST C64 PROGRAMME"
30 PRINT "TWO PLUS THREE IS";2+3
40 END

Expected result: a cleared screen, a heading and the value 5, followed by READY. Numeric PRINT output includes spacing; do not interpret a leading space as an extra digit. If Studio reports a successful build but VICE shows an error, use the BASIC error reference: the build validates source encoding and PRG structure, while the C64 ROM interprets BASIC syntax.

Change one thing at a time

Change the message, Save and Run again. Next change the arithmetic expression. Finally add a numbered line before END. Keep a known working copy with an explicit Git commit if you use source control. A small, observable change is easier to understand than copying a long programme and trying to diagnose several mistakes at once.

Each complete example in this guide identifies its language. Replace the whole configured source when trying it; do not paste a second numbered programme after an existing one. Assembly examples also contain their own .org line and return instruction. Short reference fragments illustrate syntax and are not complete projects. Expected results describe what to check in the emulator; an assembler success alone does not prove graphics, keyboard or sound behaviour.

Using the workbench

Use the shared Explorer, editor tabs, toolbar, resizable bottom panels and optional Agent sidebar. Supporting project documents open read-only. Use Source Control for explicit Git actions and Terminal for commands you type yourself. AI cannot use the terminal, Git, Build or Run.

The Emulator panel provides Run, Stop, Restart and Rebuild on save. The editor stays visible while the selected emulator uses its own window. Rebuild on save applies only to your explicit Save while a project is already running; it resets programme state. Recovery and AI saves do not authorise execution.

Unsaved source blocks builds. Save or discard before switching projects. Stop a running emulator before changing projects or tools. Recovery is local to Eightbit Studio 6502.

Understand the project files

The machine-specific manifest selects its exact target and one source under src/ (c64.toml for C64, bbc.toml for BBC Model B). The BASIC template uses src/basic/main.bas; the assembly template uses src/asm/main.asm. README.md provides project guidance and AGENTS.md records machine programming guidance for coding assistants. CLAUDE.md directs Claude to that AGENTS file, and tests/README.md provides a repeatable verification checklist. Only the chosen language’s source folder is created; existing projects keep their valid configured paths. The manifest is configuration, not a place for executable commands or linker options. A folder containing another supported family manifest is ambiguous and cannot be opened as a source project.

Use Build as a checkpoint

After Save, Build validates the current source and creates the machine media (C64 program.prg or BBC program.ssd) with build metadata. Assembly also needs the configured ca65 and sibling ld65. Read the diagnostic before changing the programme: a tool-version failure and an invalid operand require different repairs. The Build result is tied to the saved source revision and the output hash. Editing the source makes that result unsuitable for exporting the new revision until another successful build.

Export PRG or Export SSD writes a separately chosen new destination. It refuses to replace an existing file. Use a descriptive new filename for a milestone and keep the editable source in the project. A media image is executable programme data, not a backup of the project configuration, source comments or edit history. Do not edit generated build bytes to repair a source error; the next build replaces them.

Separate Studio and emulator state

The text in Studio is the source of the next build. Commands typed at the machine prompt affect only the running emulator. Editing a line in its window does not update src/basic/main.bas. Rebuild on save deliberately restarts a running project, so values, scores and temporary changes inside the emulator are reset. Turn it off when you want to examine a running programme while editing its next version.

Recover deliberately

If a source file changes outside Studio, reopen or reconcile it before saving over another revision. Read the recovery prompt rather than assuming the newest visible text is the only copy. Stop the emulator before changing project or tool settings. If a build fails after an earlier success, the last good bytes may still exist for diagnosis, but Run will not silently execute them.

Use the terminal only for commands you choose to type, such as checking an installed tool version. A programme example is BASIC or assembly source and belongs in the editor; it is not a terminal command. The optional Agent can explain a selected diagnostic or propose a source change, but cannot start tools, operate Git or control the emulator on your behalf.

Using the C64

The READY prompt

The C64 starts in BASIC. READY means that the interpreter is waiting for a command. A line without a number runs immediately: PRINT 2+3 displays a result. A numbered line is stored for later execution by RUN. This distinction explains why typing a calculation can display a value while typing 10 PRINT 2+3 merely returns to the prompt.

Studio source files always contain numbered BASIC lines. To try a direct-mode reference example in Studio, put it in a suitable numbered programme or type it yourself into VICE. Do not add READY, the screen banner or the result of a calculation to the source file.

Editing and listing

On the original BASIC screen editor, entering an existing line number replaces that line. Entering only its number deletes it. Studio instead uses ordinary text editing: remove the source line to delete it, and keep the remaining numbers increasing without duplicates. Studio rejects empty numbered lines. The machine screen editor has its own input-length and wrapping constraints; a source file accepted by Studio is not a promise that the same long line can be retyped through the original editor unchanged.

Use LIST before RUN if you suspect that the emulator is holding a different programme. NEW in VICE does not delete the Studio project. Conversely, saving the Studio source does not preserve variables currently held inside BASIC.

Keyboard and stopping

Click or focus VICE to send keyboard input to the C64. INPUT waits for a complete response followed by Return. GET reads an available character without waiting for Return. The C64 RUN/STOP key interrupts ordinary BASIC execution; the host key assigned to it depends on the VICE build and selected keyboard mapping. Consult that installation’s keyboard settings instead of assuming that every Mac uses the same shortcut.

Use Studio Stop when you need to terminate the owned emulator, including a machine-code loop that no longer services the keyboard. Stop is different from pausing a BASIC programme: it ends that emulator session. Restart builds the saved source and starts a fresh session. A C64 reset is not an automatic source-save operation.

Text and character modes

The C64 uses PETSCII and character-generator modes, not Unicode. Letter case and graphic symbols can look different after changing character mode. The supplied examples assume the usual uppercase/graphics startup mode unless stated otherwise. Studio normalises printable ASCII source to uppercase and requires CHR$ for control bytes; pasting a graphical glyph from a modern document is not a supported way to insert a PETSCII byte.

Loading and saving on a real C64

The historical machine supports device-oriented LOAD, SAVE and VERIFY commands. For example, a separately operated C64 with a suitable disk drive can use LOAD "NAME",8 and SAVE "NAME",8. The device number and secondary address belong to that machine’s setup. They are included in the language reference so that older listings make sense.

Original C64 (development): save your source, open the Emulator panel and choose Run original C64 (development). It builds a fresh standard PRG and executes it with the bundled original emulator and firmware. BASIC needs no tools or historical ROM; assembly still uses separately installed ca65/ld65. The screen can be embedded or a separate Studio window. Focus its canvas for physical keys (Escape is RUN/STOP), or use BASIC command or input. Stop ends the session; Reset cold-boots without reloading; Restart builds the current saved source. Drives, cartridges and debugging are unsupported.

The browser Project emulator selector also offers Original C64 (development) for a checked BASIC build. chips remains the initial browser choice; ordinary desktop Run retains VICE. Original glyph drawings, random sequence, transcendental approximations and conservative stack limits differ from the historical firmware. Use the retained VICE/chips route for compatibility-dependent programmes. No historical software or universal silicon compatibility is implied.

Studio’s managed VICE session injects a fresh PRG directly into RAM and disables disk, filesystem and printer devices. It does not mount your project directory or save files back into it. Use Studio Export PRG for the implemented export workflow. Drive commands in an old listing therefore need a different, explicitly configured environment; they are not steps to add to the current Run workflow.

Commodore BASIC V2

A small programme with values

BASIC lets you describe work using named values and numbered statements. The following programme stores a name and a score, changes the score, then prints both. The line numbers determine execution order; they are not instruction counts and need not be consecutive.

10 REM A FIRST SCORE CARD
20 NM$="SAM"
30 SC=120
40 SC=SC+25
50 PRINT NM$;" SCORED ";SC
60 END

Expected result: SAM SCORED followed by 145. The assignment SC=SC+25 reads the old score, adds 25 and stores the result. LET SC=120 is equivalent to SC=120. In an assignment, the equals sign stores a value; within a condition, it compares values.

Variable names and types

A name begins with a letter and may continue with letters or digits. Only the first two characters of its name are significant, with a type suffix distinguishing the kind of value. SC and SCORE can therefore collide, as can SCORE and SCENE. Use short, distinctive names such as SC for score, LI for lives and PX for a position. Avoid embedded BASIC keywords in names: tokenisation can recognise keywords even when they occur within a longer sequence of letters.

FormMeaningExample
A or SCFloating-point numeric value, including fractions.SC=12.5
A% or SC%Signed 16-bit integer variable, from -32768 through 32767.SC%=120

Numeric variables start at zero and strings at the empty string. Explicit initialisation still makes the programme easier to read and restart. Integer variables save storage in some uses but do not turn BASIC arithmetic into native integer machine code. Test ranges before storing a computed value in an integer variable.

Numbers and expressions

Write ordinary decimal numbers in BASIC, including a decimal point or scientific notation where useful. Hexadecimal $D020 notation belongs to the assembler; write the decimal address 53280 for the same register in BASIC. A string literal is enclosed in double quotation marks. A suffix such as $ is part of a variable or function name, not a currency symbol.

Parentheses make expressions easier to audit. The main order is exponentiation, unary sign, multiplication/division, addition/subtraction, comparisons, NOT, AND, then OR. Use explicit parentheses around mixed arithmetic and logical expressions rather than relying on a reader remembering every rule. String addition concatenates text; numeric addition calculates a sum. Adding a string directly to a number gives a type mismatch.

10 A=7:B=3
20 PRINT A+B;A-B;A*B;A/B
30 PRINT (A+B)*2
40 PRINT "HELLO "+"C64"
50 END

Expected result: the four arithmetic results, then 20, then HELLO C64. BASIC uses floating-point arithmetic, so some decimal fractions are approximate. Prefer an integer counter for a loop and compute a displayed fraction from it rather than repeatedly adding a fraction and expecting exact equality.

PRINT and formatting

PRINT with no items starts a new line. A semicolon keeps items adjacent using their own formatting; a comma advances to a print zone. A trailing semicolon keeps the next output on the same line. Numeric output normally reserves space for a sign and adds spacing, so PRINT "SCORE=";SC is not a byte-exact text formatter. TAB and SPC help lay out columns; STR$ converts a number to text when you need to compose a string.

Use PRINT CHR$(147) to clear the display through the screen output routine. This is a runtime control character, not a special Studio editor command. The screen article explains cursor, colour and reverse-video controls. A question mark outside a literal is shorthand for PRINT, but full keywords are easier for beginners to search.

Comments and source rules

REM consumes the rest of its physical line. A colon can separate several executable statements on a line, but a colon after REM remains part of the comment. Unlike some BASIC dialects, the apostrophe is not a BASIC V2 comment introducer. Use REM explicitly. Keep one main action per line when learning, and leave gaps of ten for later insertions.

Studio accepts line numbers 0–63999 in increasing order, printable ASCII source, closed quoted strings and at most 250 tokenised bytes per line. A source file is bounded to 128 KiB, and the encoded programme must fit below $A000. Empty unnumbered lines may separate source sections. These are source/build limits; variable, string and array storage also consumes C64 memory at runtime.

Do not transplant another BASIC dialect

Stock C64 BASIC V2 has no ELSE, WHILE, REPEAT, PRINT USING, Dragon graphics commands or SOUND statement. Use IF with explicit branches, FOR/NEXT, screen memory and hardware-register programming as shown later. RESTORE has no line-number argument. This guide keeps C64 BASIC separate from the Dragon Help even where the languages share familiar words.

Decisions, loops and subroutines

Decisions without ELSE

IF evaluates a numeric expression. Zero is false; non-zero is true. Comparisons produce -1 for true and 0 for false. THEN can introduce a statement or a target line number. BASIC V2 has no ELSE clause. Put the false path on a later line and use an explicit branch when the true path must skip it.

10 INPUT "SCORE";SC
20 IF SC>=100 THEN 60
30 PRINT "KEEP PRACTISING"
40 GOTO 70
60 PRINT "TARGET REACHED"
70 PRINT "FINISHED"
80 END

Enter 99 and then rerun with 100. Both paths should print FINISHED once. Notice that the branch to 70 prevents the false path from falling into the target message. When an IF condition is false, the rest of that numbered line is skipped, including statements after colons. Put unconditional work on a new line to make that rule visible.

Combining tests

AND, OR and NOT operate on signed 16-bit integer values. Their use with comparison results is convenient because true is all bits set. BASIC V2 does not provide a short-circuit guarantee that makes unsafe arithmetic disappear. Do not write IF D<>0 AND N/D>2 THEN ... to protect a division; test D first on a separate line, then evaluate the division only along the safe path.

10 INPUT "NUMERATOR";N
20 INPUT "DIVISOR";D
30 IF D=0 THEN 70
40 PRINT "QUOTIENT";N/D
50 END
70 PRINT "DIVISOR MUST NOT BE ZERO"
80 GOTO 20

This separates invalid input from calculation. The same approach works before taking a square root of a negative value, indexing an array or reading the first character of an empty string.

Counted loops

FOR sets a counter, a terminal value and an optional STEP. NEXT updates the counter and repeats until the limit has been passed in the direction of the step. The default step is one. Use a negative step to count down. Do not assume FOR will skip its body just because its starting value is already beyond the intended limit; pre-test the range when the body must sometimes run zero times.

10 FOR N=5 TO 1 STEP -1
20 PRINT N
30 NEXT N
40 PRINT "GO"
50 END

Expected result: 5, 4, 3, 2, 1 and GO. Avoid STEP 0 unless an intentionally endless loop is what you mean; an explicit GET loop is clearer. Give nested loops different counters and close the most recently opened loop first. Altering a FOR counter inside its body or jumping into the middle of a loop makes its bookkeeping difficult to follow.

Polling the keyboard

GET A$ returns an available character or an empty string. It does not wait for Return and is useful for menus and small games. Test for the empty string before ASC. INPUT is more convenient for complete text or numeric answers because it handles a line of editing before returning.

10 PRINT "PRESS A OR Q"
20 GET K$:IF K$="" THEN 20
30 IF K$="Q" THEN 80
40 IF K$<>"A" THEN 20
50 PRINT "A SELECTED"
60 GOTO 20
80 PRINT "GOODBYE"
90 END

Expected result: other keys are ignored; A prints a message; Q exits. Holding a key may produce repeated characters according to the machine keyboard behaviour. A game that needs newly pressed versus held keys must design those states explicitly.

Subroutines and dispatch

GOSUB saves a return position and transfers control to a numbered routine. RETURN resumes at that saved position. Put END before the subroutine area so normal execution does not fall into it. Do not enter a RETURN-ending routine with GOTO; no matching return position would have been created. BASIC variables are shared across subroutines, so document which values each routine reads and changes.

10 SC=0
20 GOSUB 1000
30 SC=SC+10
40 GOSUB 1000
50 END
1000 PRINT "SCORE";SC
1010 RETURN

Expected result: SCORE 0 then SCORE 10. Extend the routine to print lives as well, and verify that it does not unexpectedly change SC. A good small routine has a clear purpose and a predictable set of changed variables.

ON CH GOTO 100,200,300 selects a numbered destination using a one-based selector. ON CH GOSUB 1000,2000,3000 similarly calls a subroutine. A selector of zero or beyond the list normally falls through; an invalid negative or excessive value can raise an error. Validate menu input first. Use these forms when several branches have the same shape, not to obscure a simple two-way decision.

Stopping and restarting

END finishes the programme. STOP leaves a visible stoppage useful during experiments. CONT can resume only while the interpreter retains a valid continuation; editing or errors may invalidate it. A fresh RUN clears variables, so keep initialisation at the beginning rather than relying on values left from a previous attempt.

Strings, arrays and data

Strings are sequences of characters

A string stores text, including an empty string of length zero. LEN gives its length. LEFT$, RIGHT$ and MID$ select parts without modifying the original. BASIC V2 uses one-based positions for MID$: the first character is position 1. Check a string is non-empty before ASC, because ASC("") is an illegal quantity.

10 A$="COMMODORE"
20 PRINT LEN(A$)
30 PRINT LEFT$(A$,3)
40 PRINT MID$(A$,4,2)
50 PRINT RIGHT$(A$,4)
60 END

Expected results: 9, COM, MO and DORE. To replace a character, construct a new string from the prefix, replacement and suffix. BASIC V2 does not support assigning into MID$ as some later dialects do. Keep the total at or below 255 characters and avoid repeatedly joining very large temporary strings in a fast loop.

Converting input

INPUT N asks for a numeric response. INPUT A$ asks for text. For one-key input use GET A$ and inspect it before converting. VAL converts an initial numeric part of a string; it does not guarantee that the entire string is a valid number. VAL("12X") can therefore be a poor validation test for a strict numeric field.

10 PRINT "PRESS A DIGIT 0 TO 9"
20 GET K$:IF K$="" THEN 20
30 C=ASC(K$)
40 IF C<48 THEN 20
50 IF C>57 THEN 20
60 N=C-48
70 PRINT "YOU CHOSE";N
80 END

Expected result: letters are ignored and a digit is converted to its value. This is an intentionally bounded one-character input format. For a longer answer, collect a string with an explicit maximum length and validate each character before calculation. A full text-entry editor also needs deletion and termination handling.

Arrays and bounds

DIM reserves an indexed set of values. DIM SC(3) provides four elements, numbered 0 through 3. The declared number is the upper bound, not the number of entries. String arrays use a $ suffix and integer arrays a % suffix. A two-dimensional array such as DIM B(3,2) has four times three elements. Storage rises with the product of the dimensions, so calculate the budget before declaring a large table.

Undimensioned arrays receive a default upper bound of ten when first used, but relying on this hides mistakes. DIM once near startup, before the first use. Repeating a DIM for the same array during a loop gives REDIM’D ARRAY. Use indices within the declared bounds and initialise each value that your programme depends on.

10 DIM NM$(2),SC(2)
20 FOR I=0 TO 2
30 READ NM$(I),SC(I)
40 NEXT I
50 FOR I=0 TO 2
60 PRINT NM$(I);" ";SC(I)
70 NEXT I
80 END
100 DATA "ADA",40,"BEN",55,"CY",30

Expected result: three names and their scores. The DATA line is part of the programme even though it follows END; READ searches the stored data stream rather than executing DATA as ordinary work. Try changing one score and rebuilding. Then deliberately attempt SC(3) to understand the bounds error before restoring the valid programme.

READ and RESTORE

READ takes successive DATA items into variables. Keep the destination type compatible with the item: text into a numeric destination raises a type mismatch. DATA is literal text, not a place for evaluated expressions. READ does not turn a stored expression such as 2+3 into the number 5. Quote text when commas, colons or leading/trailing spaces are significant.

10 DATA 3,6,9
20 READ A,B,C
30 PRINT A;B;C
40 RESTORE
50 READ D
60 PRINT "FIRST AGAIN";D
70 END

Expected result: 3, 6, 9, then FIRST AGAIN 3. Bare RESTORE resets the data pointer to the first DATA item. C64 BASIC V2 does not accept RESTORE 100. To select one of several tables, use a known count and skip items deliberately, or load tables into arrays once and index them thereafter.

Search and aggregate

A table makes many operations share the same control structure: initialise an accumulator, visit each valid index, and update the result. The following example totals three scores. Initialise TT before the loop so another run or a subroutine call cannot accidentally reuse the previous sum.

10 DIM SC(2)
20 DATA 40,55,30
30 TT=0
40 FOR I=0 TO 2
50 READ SC(I)
60 TT=TT+SC(I)
70 NEXT I
80 PRINT "TOTAL";TT
90 PRINT "AVERAGE";TT/3
100 END

Expected result: total 125 and an average near 41.6667, subject to BASIC’s display precision. Extend the programme to find the highest score. Start the maximum from the first stored value rather than zero if negative values might be valid.

Memory and data lifetime

RUN and CLR discard variables and array contents. DATA remains in programme text and can be read again. Variable storage, array descriptors and strings share the BASIC memory budget with the programme. FRE reports available BASIC memory and can trigger string garbage collection; it is not a measure of all physical RAM. A short listing can still exhaust memory by dimensioning a large array or creating many strings.

BASIC statement reference

How to read this reference

Forms are written with optional parts in square brackets and alternatives in words. Do not type the brackets. Examples in this table are fragments, often suitable at READY or inside a numbered line; they are not complete Studio source files. A keyword’s presence in BASIC V2 does not mean Studio exposes every historical device it can operate. See the device notes beside OPEN, LOAD, SAVE and related forms.

The table is alphabetical. Compound forms such as DEF FN, INPUT# and ON ... GOSUB have their own explanations. TO, STEP, THEN and FN are parts of other forms, not independent commands. Operators and numeric/string functions are described in the next article.

CLR

Syntax: CLR. Discard variables, arrays and runtime control state while retaining programme text. Use during deliberate reinitialisation at READY.

Example: CLR. Remember: It is not a source-file save and does not erase the Studio editor.

CLOSE

Syntax: CLOSE logicalFile. Close a logical file previously opened by OPEN.

Example: CLOSE 2. Remember: Only meaningful for an opened channel. Managed Run provides no disk or printer workflow.

CMD

Syntax: CMD logicalFile [, output]. Redirect ordinary output to an opened logical output channel, optionally sending an item.

Example: CMD 2. Remember: Historical device operation. Restore normal output before closing the channel; do not expect an available printer in Studio.

CONT

Syntax: CONT. Continue after STOP or RUN/STOP if the interpreter still has a valid continuation.

Example: CONT. Remember: Editing programme text or encountering an error can make continuation unavailable. Use RUN when a fresh start is intended.

DATA

Syntax: DATA item [, item ...]. Store literal values for READ. Items are encountered in programme order, independently of normal execution flow.

Example: DATA 12,"NORTH",24. Remember: Expressions are not calculated here. Quote text with commas or colons. Keep destination types compatible.

DEF FN

Syntax: DEF FN name(argument)=expression. Define a numeric function of one numeric argument, then call it using FN.

Example: DEF FN F(X)=X*X+1. Remember: Define it in programme mode before calling FN F(3). Other variables used in the expression are shared programme values.

DIM

Syntax: DIM name(upperBound [, upperBound ...]) [, ...]. Allocate arrays with inclusive upper bounds.

Example: DIM SC(4),NM$(4). Remember: This gives five elements per array, from 0 through 4. Dimension once before use and budget multidimensional storage.

END

Syntax: END. Finish execution without deleting programme text.

Example: END. Remember: Put END before subroutine or data-support code when normal fall-through would be wrong.

FOR

Syntax: FOR variable=start TO limit [STEP increment]. Initialise a counted loop closed by NEXT.

Example: FOR I=1 TO 10 STEP 2. Remember: TO and STEP belong to this form. Pre-test if the loop must sometimes execute zero times; avoid a zero step.

GET

Syntax: GET variable [, variable ...]. Read available characters without waiting for Return.

Example: GET K$. Remember: Prefer a string for keyboard input. An empty string means no key was available. Test before calling ASC.

GET#

Syntax: GET# logicalFile, variable [, variable ...]. Read characters from a previously opened input channel.

Example: GET# 2,A$. Remember: GET# is formed from GET and #, not a separate token. Device-backed use is outside managed Run.

GOSUB

Syntax: GOSUB line. Call a numbered subroutine and remember the return position.

Example: GOSUB 1000. Remember: Every reached exit must have a matching RETURN. Do not fall into a subroutine from the main programme.

GOTO

Syntax: GOTO line. Continue execution at an existing numbered line.

Example: GOTO 100. Remember: GO TO is the spaced form using the GO and TO tokens. Studio does not provide Dragon-style multi-file target resolution.

IF

Syntax: IF expression THEN statement-or-line. Execute the rest of the numbered line only when the condition is non-zero.

Example: IF SC>=100 THEN 500. Remember: There is no ELSE. A false IF skips later colon-separated statements on the same line.

INPUT

Syntax: INPUT ["prompt";] variable [, variable ...]. Wait for a line of keyboard input and assign values.

Example: INPUT "NAME";NM$. Remember: Numeric destinations require numeric input. For robust constrained input, GET into a string and validate explicitly.

INPUT#

Syntax: INPUT# logicalFile, variable [, variable ...]. Read fields from an already opened input channel.

Example: INPUT# 2,A$,N. Remember: No interactive prompt is supplied. Field shape and destination type must match the file; managed Run has no disk input.

LET

Syntax: [LET] variable=expression. Assign a computed value to a scalar or array element.

Example: LET SC=SC+10. Remember: LET is optional. Assign compatible string or numeric types and check integer ranges.

LIST

Syntax: LIST [first[-last]]. Display all stored lines or a selected range at the C64 prompt.

Example: LIST 100-200. Remember: A direct-mode inspection command. Studio displays editable source itself; LIST output is not source to paste back verbatim.

LOAD

Syntax: LOAD ["name" [, device [, secondary]]]. Historical file loading into the C64. The device and secondary address control source and loading behaviour.

Example: LOAD "DEMO",8. Remember: Disk/file access is disabled in managed Run. Loading from inside a programme has special continuation effects; it is not an import API for Studio.

NEW

Syntax: NEW. Remove the programme and variables from the current BASIC machine session.

Example: NEW. Remember: It does not remove the Studio project. Keep source saved before experimenting with machine-session commands.

Syntax: NEXT [variable [, variable ...]]. Advance one or more active FOR loops.

Example: NEXT I. Remember: Close nested loops from innermost outward. A missing or wrong active counter can produce NEXT WITHOUT FOR.

ON

Syntax: ON selector GOTO/GOSUB line [, line ...]. Choose a one-based branch or subroutine from a list.

Example: ON CH GOSUB 1000,2000,3000. Remember: Validate selectors. Zero or a value beyond the available list can fall through instead of selecting an item.

OPEN

Syntax: OPEN logicalFile [, device [, secondary [, "name"]]]. Create a logical connection to an input or output device.

Example: OPEN 2,8,2,"DATA,S,R". Remember: Historical disk example only. A logical file number is not the same thing as a physical device number. Managed Run does not mount drives.

POKE

Syntax: POKE address,value. Write a byte to a decimal memory or I/O address.

Example: POKE 53280,6. Remember: Use address 0–65535 and byte 0–255. Valid numeric ranges do not make every address safe to overwrite; consult the memory map.

PRINT

Syntax: PRINT [item [separator item ...]]. Send text and values to the current output channel, normally the screen.

Example: PRINT "SCORE";SC. Remember: Semicolon joins output; comma advances through zones. A trailing separator keeps output on the line. ? is shorthand outside literals.

PRINT#

Syntax: PRINT# logicalFile [, items]. Send formatted output to an opened logical file.

Example: PRINT# 2,A$. Remember: Device-backed use is outside managed Run. Design delimiters deliberately when another programme will use INPUT# to read the data.

READ

Syntax: READ variable [, variable ...]. Consume successive literal DATA items.

Example: READ NM$,SC. Remember: Too few items gives OUT OF DATA. A non-numeric item for a numeric destination gives TYPE MISMATCH.

REM

Syntax: REM comment. Treat the rest of the physical line as a comment.

Example: REM UPDATE THE SCORE. Remember: A colon after REM does not restart execution. Use REM rather than an apostrophe comment from another dialect.

RESTORE

Syntax: RESTORE. Reset the READ position to the first DATA item.

Example: RESTORE. Remember: BASIC V2 has no RESTORE line-number argument. Read and skip a known count or store tables in arrays.

RETURN

Syntax: RETURN. Resume after the most recent GOSUB.

Example: RETURN. Remember: Use only when a matching call exists. END the main programme before its subroutine area.

RUN

Syntax: RUN [line]. Clear variables and begin the stored BASIC programme, optionally at a selected line.

Example: RUN 100. Remember: Starting in the middle skips earlier setup. Studio Run additionally builds a fresh PRG and starts VICE; that is a host workflow, not BASIC syntax.

SAVE

Syntax: SAVE ["name" [, device [, secondary]]]. Save the stored BASIC programme through the selected historical device.

Example: SAVE "DEMO",8. Remember: Managed Run has no disk/filesystem save channel. Use Studio Save for source and Export PRG for a new output file.

STOP

Syntax: STOP. Stop execution and retain a potential continuation.

Example: STOP. Remember: Use for a deliberate checkpoint. Studio Stop ends the emulator process and cannot be resumed by BASIC CONT.

SYS

Syntax: SYS address. Call machine code at a decimal address.

Example: SYS 2061. Remember: Only call code actually present at that address with a valid return convention. Studio assembly adds its own SYS2061 loader; do not add another.

VERIFY

Syntax: VERIFY ["name" [, device [, secondary]]]. Compare a stored programme with a file through a historical device.

Example: VERIFY "DEMO",8. Remember: This is not Studio build-hash verification and does not work as a disk workflow in managed Run.

WAIT

Syntax: WAIT address,mask [, exclusiveOr]. Poll until the byte read, optionally XORed with the third argument and ANDed with the mask, is non-zero.

Example: WAIT 53265,128. Remember: It can wait indefinitely and does not offer a BASIC timeout. Use explicit bounded polling for recoverable beginner examples; repeated reads alone do not synchronise a complete animation frame.

Special values and control syntax

ST (also called STATUS) reports I/O status; inspect it immediately after the relevant device operation. TI (TIME) is the jiffy clock and TI$ (TIME$) is its six-digit HHMMSS representation. Assign TI$="000000" to reset that clock deliberately. It is a machine timer, not a modern wall clock, and it depends on the normal operating-system interrupt service. The timer wraps; subtracting readings across a reset or wrap requires explicit handling.

BASIC functions and operators

Functions transform values

Use a function where an expression is expected: PRINT LEN(A$), N=INT(X), or IF ABS(D)>10 THEN 200. String functions end in $ where they return a string. A type suffix is part of the name and must not be omitted. Validating an argument first often produces a much clearer programme than letting the interpreter stop with a generic error.

ABS

Form: ABS(x). Absolute numeric magnitude.

Example: ABS(-7) gives 7. Remember: Use when only distance from zero matters.

ASC

Form: ASC(text$). Code of the first character.

Example: ASC("A") gives 65 in the example encoding. Remember: The empty string is invalid. A PETSCII code is not automatically a screen code.

Example: ATN(1)*4 approximates pi. Remember: Convert units explicitly when the user thinks in degrees.

Example: PRINT CHR$(147) clears the normal text screen. Remember: Control characters act when printed; they are not visible decimal text.

Example: COS(0) gives 1. Remember: Convert degrees using radians=degrees*pi/180.

EXP

Form: EXP(x). The exponential function e raised to x.

Example: EXP(0) gives 1. Remember: Large positive inputs overflow the numeric range.

FN

Form: FN name(x). Evaluate an earlier DEF FN definition.

Example: After DEF FN F(X)=X*X, FN F(4) gives 16. Remember: Define the function in programme mode before calling it.

FRE

Form: FRE(x). Available BASIC memory, with string collection effects.

Example: FRE(0) requests the current result. Remember: Values above 32767 can be reported as negative; add 65536 to a negative result for an unsigned count. Do not use it as a total physical-RAM test.

INT

Example: INT(2.9) gives 2; INT(-2.1) gives -3. Remember: It rounds down, not towards zero. This difference matters with negative values.

Form: LEN(text$). Number of characters in a string.

BASIC errors and recovery

Locate the failing operation

BASIC runtime messages appear in the VICE window, commonly as ?NAME ERROR IN line. The number is the BASIC source line, not its row in Monaco. INPUT can also issue recoverable messages such as ?REDO FROM START or ?EXTRA IGNORED. The catalogue below includes those messages as well as the standard errors; it does not pretend they are all fatal errors.

First read the line and inspect the values that reach it. Fix the source in Studio, Save and Run again. Editing only the running C64’s copy does not update the project. Studio build errors such as DC64100 are separate from messages printed by the ROM.

BAD DATA

Cause: Input read through INPUT# does not match the expected field type.

Example: A file field containing text is read into a numeric variable.

Recovery: Check the record format, separators and destination types. Device input is outside managed Run; reproduce file problems only in an appropriate separately configured environment.

BAD SUBSCRIPT

Cause: An array index is outside its allocated bounds or has an invalid dimension shape.

Example: DIM A(2) followed by PRINT A(3).

Recovery: Inspect the failing index and the DIM statement. Bounds are inclusive: DIM A(2) allows 0, 1 and 2. Fix the loop limit before increasing storage.

CAN'T CONTINUE

Cause: CONT has no valid saved execution position.

Example: Attempt CONT after editing the programme or after an error.

Recovery: Start again with RUN, passing through initialisation. Use small saved checkpoints in source instead of relying on continuation after arbitrary changes.

DEVICE NOT PRESENT

Cause: The requested peripheral does not respond.

Example: LOAD "DEMO",8 without an available drive.

Recovery: Check the actual environment. Disk/filesystem devices are disabled in Studio’s managed session, so use Export PRG rather than trying to repair this by adding drive commands.

DIVISION BY ZERO

Cause: A division attempts to use zero as its divisor.

Example: PRINT 10/0.

Recovery: Validate the divisor on a separate line before evaluating the quotient. An AND expression is not a safe substitute for control flow.

EXTRA IGNORED

Cause: Keyboard INPUT received more fields than there are destinations.

Example: INPUT A receives two comma-separated answers.

Recovery: Enter the requested number of items or change the INPUT destinations. This is an input warning rather than proof that every extra item was stored.

FILE NOT FOUND

Cause: A device could not locate the requested file.

Example: LOAD names a file absent from the chosen device.

Recovery: Check the name and device in a separately configured file workflow. The managed session has no mounted project files.

FILE NOT OPEN

Cause: A logical channel is used before it has been opened.

Example: PRINT# 2,"X" when logical file 2 is not open.

Recovery: Audit the OPEN/use/CLOSE order and the logical file number. Do not confuse a logical channel number with a drive number.

FILE OPEN

Cause: A logical file number is opened while already in use.

Example: The same OPEN runs twice without closing its channel.

Recovery: Close the intended channel or choose a deliberate distinct number. Avoid branching back through setup while retaining the old connection.

FORMULA TOO COMPLEX

Cause: An expression requires more internal temporary processing than BASIC can provide.

Example: A deeply nested or long string expression exceeds the interpreter’s evaluation capacity.

Recovery: Break the operation into intermediate assignments. Keep temporary strings short and remove unnecessary nested expressions.

ILLEGAL DIRECT

Cause: A statement requiring programme context is used directly at READY.

Example: Enter a DEF FN definition as an immediate command.

Recovery: Put the operation into a numbered programme and RUN it. Studio already requires numbered source; do not paste a transcript containing prompt commands into the file.

ILLEGAL QUANTITY

Cause: A numeric argument is outside the operation’s allowed range.

Example: POKE 53280,256 or PRINT SQR(-1).

Recovery: Inspect each argument, including values produced by expressions. Range-check addresses, bytes, substring positions and function domains before calling them.

LOAD

Cause: A tape-loading operation encounters a loading problem.

Example: An incomplete or unreliable cassette read fails.

Recovery: On a separately operated machine, check the medium and loading setup. Studio injects a fresh PRG rather than using cassette playback; treat a managed-session startup failure through Studio’s emulator diagnostics.

NEXT WITHOUT FOR

Cause: NEXT has no matching active FOR loop.

Example: A branch jumps directly to NEXT I without executing FOR I.

Recovery: Trace the branch into the loop and match nested counters. Keep loop entry at FOR and exits explicit.

NOT INPUT FILE

Cause: Input is attempted on a file opened for another direction.

Example: INPUT# uses a logical channel opened for writing.

Recovery: Correct the file mode and channel selection. This is a historical device-channel error, not a Studio source encoding failure.

NOT OUTPUT FILE

Cause: Output is attempted on a file opened for another direction.

Example: PRINT# uses a logical channel opened for reading.

Recovery: Open the intended output channel before use and close it afterwards in an environment that provides that device.

OUT OF DATA

Cause: READ has consumed all available DATA items.

Example: Four variables are read from a three-item data table.

Recovery: Count the items and reads, including reads inside loops. Use RESTORE only when restarting the data stream is intended; do not hide a missing item by resetting it on every read.

OUT OF MEMORY

Cause: BASIC cannot allocate required programme/runtime storage or control-stack space.

Example: A very large array or unbounded recursive GOSUB exhausts the available memory.

Recovery: Reduce array bounds and temporary strings, or fix runaway calls. A successful PRG build only checks programme bytes; it does not reserve all memory that the programme may allocate at runtime.

OVERFLOW

Cause: A numeric calculation exceeds the representable range.

Example: An excessively large positive argument to EXP.

Recovery: Choose a smaller range, scale intermediate calculations or reject the input before evaluating the expression.

REDIM'D ARRAY

Cause: DIM attempts to allocate an array that already exists.

Example: DIM A(5) executes again on the second pass through a loop.

Recovery: Dimension once near startup. Also check for an earlier use that implicitly allocated the array. Use RUN for a clean start when testing changed allocation.

REDO FROM START

Cause: Keyboard INPUT could not interpret the supplied value for its destinations.

Example: Type letters in response to a numeric INPUT.

Recovery: Enter a compatible value. For a controlled user interface, read a string and validate it instead of relying on the generic numeric prompt.

RETURN WITHOUT GOSUB

Cause: RETURN is executed without a pending subroutine call.

Example: Main code falls through into a routine ending in RETURN.

Recovery: Put END before the routine area, and enter it with GOSUB rather than GOTO. Check every exit path.

STRING TOO LONG

Cause: A string would exceed 255 characters.

Example: Repeated concatenation grows A$ beyond the maximum length.

Recovery: Check LEN before appending. Store separate records or process smaller pieces rather than building one oversized string.

SYNTAX

Cause: The interpreter cannot parse the statement as BASIC V2.

Example: IF X=1 THEN PRINT "YES" ELSE PRINT "NO" uses an unavailable ELSE.

Recovery: Check spelling, punctuation, brackets, separators and dialect. Inspect the indicated numbered line. Studio tokenisation can succeed even though runtime syntax is invalid.

TOO MANY FILES

Cause: Too many logical channels are open.

Example: Repeated OPEN operations allocate channels without matching CLOSE operations.

Recovery: Close channels when their work ends and bound how many can be open simultaneously. Managed Run does not provide disk/printer usage to exercise this workflow.

TYPE MISMATCH

Cause: A string is used where a number is needed, or vice versa.

Example: N="TEN" or READ N consumes a text DATA item.

Recovery: Match variable suffixes and values. Use VAL or STR$ only when conversion is intended and validate its result appropriately.

UNDEF'D FUNCTION

Cause: FN calls a function that has not been defined along the executed path.

Example: PRINT FN F(2) occurs before its DEF FN F(X) line.

Recovery: Define the function before its first use and check its name. Starting RUN at a later line can skip the definition.

UNDEF'D STATEMENT

Cause: A branch refers to a line number absent from the programme.

Example: GOTO 900 after line 900 was removed.

Recovery: Check GOTO, GOSUB, IF and ON destinations after edits. Use actual programme line numbers, not editor line positions.

VERIFY

Cause: The loaded comparison data differs from the programme in memory.

Example: VERIFY compares an older saved file with an edited programme.

Recovery: Check the file/version and device in the historical workflow. For Studio exports, rebuild the saved revision and use a new destination; BASIC VERIFY is not the Studio hash check.

BREAK and a deliberate experiment

BREAK is a stoppage notice, for example after RUN/STOP or STOP, rather than a misspelt command. CONT may resume if the continuation is still valid. If a machine-code programme no longer services input, Studio Stop terminates the owned emulator.

To practise diagnosis, create a small BASIC programme containing a divisor variable set to zero and PRINT 10/D. Observe the error, then add a separate IF D=0 branch before the division. The corrected version should display your own useful explanation and avoid the runtime error. Keep this intentional failure separate from examples labelled as successful complete programmes.

6502 processor reference

Think in bytes and addresses

The NMOS 6502 executes small operations on bytes. A byte holds an unsigned value from 0 through 255. A 16-bit address selects a location from $0000 through $FFFF. The C64’s 6510 executes this documented instruction set and adds a machine-specific I/O port used for memory configuration. The CPU model explains instructions; the C64 memory map explains what an address means in this machine.

RegisterWidthPractical role
A8 bitsAccumulator: the main arithmetic, logic and byte-load/store register.
X8 bitsIndex, loop counter and register-transfer participant.
Y8 bitsIndex and loop counter, also used after indirect pointer lookup.
SP8 bitsStack offset within page $0100–$01FF.
PC16 bitsInstruction address; updated by instruction length, branches, jumps and returns.
PStatus bitsRecords arithmetic conditions and processor control state.

A, X and Y are separate registers. Loading X does not also load A. Most arithmetic operates on A; use TAX, TXA, TAY and TYA when an index value must move to or from it. A register is not a variable name in RAM: its value lasts only until an instruction changes it.

Number notation and byte order

ca65 accepts decimal numbers, hexadecimal prefixed with $ and binary prefixed with %. The # character means an immediate value. LDA #$20 loads the byte $20; LDA $20 reads memory at zero-page address $20. Multi-byte addresses are little-endian: a word $1234 is stored as byte $34 followed by byte $12.

Use <label and >label to obtain the low and high address bytes in supported expressions, for example when initialising a pointer. A .word label stores those bytes in the correct order. These operators are assembler expression syntax, not runtime instructions. Studio permits a restricted set of directives and operands; consult the project article before borrowing syntax from another assembler.

The status byte pushed onto the stack also includes a B indication and a set bit 5. B is not an ordinary persistent flag that you can branch on or set with a dedicated instruction: PHP/BRK and hardware interrupt entry differ in the pushed representation. Do not treat every bit in a saved status byte as an independently writable CPU register.

Instructions set different subsets of flags. LDA sets N and Z but leaves C unchanged. STA changes no flags. CMP sets N, Z and C without changing A. A subroutine may change flags even if it preserves a register. Place a branch immediately after the test it is meant to use, unless the intervening instruction is deliberately known to preserve that test.

The stack and calls

The hardware stack occupies $0100–$01FF. A push writes at $0100+SP and then decrements SP; a pull increments SP before reading. It has only 256 byte positions and no automatic overflow protection. BASIC, KERNAL calls and interrupts share it with your assembly. Never treat the whole page as free scratch space.

JSR saves the return information and transfers control to a routine. RTS reconstructs the address of the following instruction. PHA/PLA save and restore A; PHP/PLP save and restore status. There are no PHX, PLX, PHY or PLY instructions on the documented NMOS 6502. Save X or Y through A or in owned memory. Balance every push with a pull on every exit path.

Timing and instruction families

Instructions take different numbers of cycles. Some indexed reads gain a cycle when an address crosses a page; a taken branch also has additional cost, with another cycle when it crosses a page. The C64 video hardware can take bus time, so a sum of CPU instruction cycles alone is not a complete model of display timing. Begin with correct bounded programmes before trying raster-sensitive code.

Use the documented NMOS instructions in this guide. 65C02 instructions such as BRA, STZ and PHX, 65816 width changes and undocumented opcodes are outside the implemented source contract. The 6502 has neither a general multiply/divide instruction nor a 16-bit accumulator: software combines byte operations to implement those jobs.

Zero page is shared machine state

Zero-page addressing is compact and often faster, but the C64 operating system already uses many of those locations. An example operand in the table is a syntax illustration, not permission to overwrite every nearby byte. The machine-memory article identifies a small conventional user workspace and the need to preserve it when returning to BASIC.

Zero-page indexed arithmetic wraps at $FF. A base of $F0 plus X=$20 addresses $10, not $0110. By contrast, absolute indexed arithmetic crosses into the next page. This difference is useful when intentional and destructive when overlooked. Pointer fetches for the zero-page indirect modes also wrap their pointer-byte locations within zero page.

Walk a table using an index

.org $080D
    ldx #0
copy:
    lda message,x
    sta $0400,x
    lda #1
    sta $D800,x
    inx
    cpx #5
    bne copy
    rts

    .byte 3,54,52,32,1

Expected result: the five screen codes display C64 A in white at the top-left of the default text screen. The table contains screen codes, not the PETSCII string bytes used by CHROUT. X starts at zero and stops at five, so the last read is message+4. The test after INX determines the loop count.

Choose the legal mode for the register

LDA has more addressing choices than LDX and LDY. LDX supports absolute,Y while LDY supports absolute,X. STX and STY also have narrower choices. Do not assume an opcode works with every mode just because another load or store does. The instruction table lists the supported mode families and ca65 rejects combinations that have no NMOS encoding.

An assembler may choose zero-page encoding for a known low address. Forward labels and expression forms can affect mode selection, so inspect real build results when exact timing or byte count matters. Studio does not accept arbitrary segment/linker controls to force a different memory plan.

Branch distance and the NMOS indirect-jump quirk

A relative branch reaches -128 through +127 bytes from the following instruction. Adding data or code can move a target out of range. Replace a long conditional branch with the inverse short branch around an absolute JMP, keeping the intended fall-through clear. Do not insert undocumented long-branch syntax from another assembler.

On the NMOS processor, JMP through an indirect pointer ending at $xxFF fetches its high byte from $xx00 rather than the next page. Place such two-byte jump pointers away from page ends. This is different from adding an index to an ordinary absolute address. The 65C02 changes some behaviour, so its documentation is not interchangeable with the C64’s NMOS model.

6502 instruction reference

Documented NMOS mnemonics

This is the complete documented mnemonic set accepted by the current source policy. “zp” means zero page. Flag descriptions assume ordinary binary arithmetic unless a decimal-mode note says otherwise. “None” describes the instruction itself; code reached by a call, interrupt or jump can of course change state. ca65 still checks exact operand ranges and available encodings.

ADC

A + operand + C → A. Flags: N Z C V. Modes: immediate, zero page, zero page,X, absolute, absolute,X/Y, (zp,X), (zp),Y. Use CLC for the first byte of ordinary addition. D selects decimal behaviour.

AND

A AND operand → A. Flags: N Z. Modes: same data modes as ADC. Clear unwanted bits with a mask; other flags, including C, are retained.

ASL

Shift left, zero into bit 0. Flags: N Z C. Modes: A, zero page, zero page,X, absolute, absolute,X. Old bit 7 enters C. Memory forms are read/modify/write operations.

BCC

Branch if C=0. Flags: none. Modes: relative. After CMP, unsigned A is below the operand.

BCS

Branch if C=1. Flags: none. Modes: relative. After CMP, unsigned A is greater than or equal to the operand.

BEQ

Branch if Z=1. Flags: none. Modes: relative. Equality only when the preceding flag-setting operation represents the intended comparison.

BIT

A AND memory tested; memory bits 7/6 → N/V. Flags: N Z V. Modes: zero page, absolute. Z comes from the AND test; A is unchanged. NMOS BIT has no immediate form.

BMI

Branch if N=1. Flags: none. Modes: relative. Tests the sign bit; not a complete signed less-than test after overflow.

BNE

Branch if Z=0. Flags: none. Modes: relative. Often closes a counted loop after DEX or CPX.

BPL

Branch if N=0. Flags: none. Modes: relative. Tests non-negative result bit interpretation, including zero.

BRK

Software interrupt entry. Flags: I; stack status representation. Modes: implied with a following signature byte. Uses the IRQ/BRK vector and saves a return address two bytes past its opcode. It is not Studio’s Stop action.

BVC

Branch if V=0. Flags: none. Modes: relative. No signed overflow from the operation that last set V.

BVS

Cycle costs without false precision

For orientation, immediate LDA takes two CPU cycles, absolute STA four, JSR six and RTS six. An untaken conditional branch takes two; a taken one takes three, or four if its destination crosses a page. Indexed read timing depends on opcode and page crossing, while indexed writes have their own fixed rules. Use an authoritative per-opcode timing table for cycle-sensitive work and account for the C64 video bus; these examples do not claim raster-exact timing.

6502 arithmetic and comparisons

A byte has an interpretation

The bit pattern $FF is 255 when treated as unsigned and -1 when treated as signed two’s complement. The CPU does not attach a type label to it. Your programme chooses the interpretation and branches accordingly. Addition wraps to the low eight bits; carry and overflow describe different information about that result.

Unsigned addition uses C to report a ninth bit. Signed addition uses V to report that the mathematical answer cannot fit into -128 through 127. For example, $7F+1 gives $80 with signed overflow even though there is no unsigned carry. $FF+1 gives zero with unsigned carry. Do not use BCS as a general signed-overflow check.

Single-byte arithmetic

Start ordinary addition with CLC, then ADC. Start ordinary subtraction with SEC, then SBC. SBC subtracts both the operand and an incoming borrow represented by C=0. Forgetting the initial carry setup introduces a one-off error that can depend on whichever earlier instruction last changed C. CLD selects binary arithmetic explicitly for routines that need it.

.org $080D
    cld
    clc
    lda #7
    adc #2
    sta result
    clc
    adc #48
    jsr $FFD2
    lda #13
    jsr $FFD2
    rts
result:
    .byte 0

Expected result: the digit 9 and a line break. The conversion adds the PETSCII code for zero, so it works only for a result from 0 to 9. It is deliberately not a general decimal-printing routine. The saved result is a numeric byte; the byte sent to CHROUT is a character.

Adding and subtracting words

Store a word low byte first. Add the low bytes with CLC/ADC, then add the high bytes with ADC without clearing C again. The low-byte carry becomes part of the high-byte sum. Subtraction similarly starts with SEC on the low byte and propagates its no-borrow state into the high-byte SBC.

.org $080D
    cld
    clc
    lda left
    adc right
    sta sum
    lda left+1
    adc right+1
    sta sum+1
    lda sum
    cmp #0
    bne failed
    lda sum+1
    cmp #2
    bne failed
    lda #5
    sta $D020
    rts
failed:
    lda #2
    sta $D020
    rts
left:
    .word 255
right:
    .word 257
sum:
    .word 0

Expected result: a green border, because 255+257 is 512 ($0200). Red indicates that the explicit byte checks failed. This gives visible evidence without requiring an integrated debugger. The final ADC carry would additionally report a result beyond 65535, which this small test does not generate.

Unsigned comparison

CMP, CPX and CPY subtract for flags without retaining the difference. Equality sets Z. Carry set means the register is greater than or equal to the operand as an unsigned byte; carry clear means below. Use BCC for unsigned less-than, BCS for greater-than-or-equal, and BEQ/BNE for equality. To require strictly greater-than, exclude equality as well.

For an unsigned word, compare the high bytes first. If they differ, they determine the order. Compare the low bytes only when the high bytes match. Comparing only the low byte makes 256 appear smaller than 255. Multi-byte counters and bounds should be designed as words from the beginning rather than patched after an 8-bit wrap.

Signed comparison

N alone is not a reliable signed less-than result after subtracting values that can overflow. CMP leaves V unchanged, so a signed N-versus-V test must not assume CMP produced a fresh overflow flag. One simple signed-byte ordering technique flips bit 7 in both values and uses an unsigned comparison. For variable operands, store one transformed value in owned scratch memory, then compare the other transformed value against it.

Alternatively use binary SBC with SEC and interpret N XOR V, preserving the flags until both have been examined. The 6502 has no single signed-less-than branch. Choose a clear method and test -128, -1, 0, 1 and 127, plus equal pairs, rather than extrapolating from positive-only tests.

Shifts, masks and BCD

ASL multiplies an unsigned byte by two modulo 256 and sends the lost high bit to C. LSR divides an unsigned byte by two, discarding the fractional half into C. ROL and ROR include the previous carry, making chains of bytes possible. For a word shifted left, use ASL on the low byte followed by ROL on the high byte. A signed right shift needs to preserve the sign bit deliberately; LSR alone always inserts zero.

AND clears bits outside a mask, ORA sets selected bits and EOR toggles them. Use read-mask-write only on hardware registers for which that sequence is appropriate. Read/modify/write instructions such as INC or ASL on NMOS hardware can issue more than one write on the bus; a memory byte and an I/O control register are not interchangeable.

SED makes ADC/SBC operate on packed binary-coded decimal digits. On NMOS 6502, some resulting flags do not describe the adjusted decimal answer in the intuitive binary way, and interrupt entry does not automatically clear D. Keep beginner arithmetic in CLD binary mode and restore a valid machine environment before returning. Do not introduce decimal arithmetic into an interrupt-enabled BASIC environment without designing the interaction.

What the toolchain does

The editor contains human-readable assembly source. ca65 translates the allowed instructions and data declarations into an object file; ld65 links that object into the fixed memory layout selected by Studio. Studio then packages the bytes as a PRG with a load address and the BASIC SYS loader. A successful build means those stages accepted the input; it does not prove that the programme will return, display the intended pixels or preserve machine state.

One source, one origin

The configured .asm file is the complete source of the build. Begin with .org $080D, use a simple colon-ended label on its own line or before an instruction, and put at most one instruction on each line. A semicolon begins an assembly comment. Label names begin with a letter or underscore and continue with letters, digits or underscores. ca65 labels are case-sensitive; keep a consistent spelling.

Studio allows documented NMOS mnemonics and the four listed directives. It does not allow constant-definition statements, .include, .incbin, .macro, .proc, .segment, .import or .export. The full ca65 manual describes many features beyond this subset. Copy the patterns in this guide rather than a complete external build script. Numeric hardware addresses appear explicitly in the examples because a separate equate directive is not part of this contract.

The first output byte at $080D must be the first instruction to execute. Place data after an RTS or branch around it. An origin declaration is not a runtime jump, and a label does not stop fall-through. A programme beginning with a table will attempt to execute its table bytes when the SYS loader runs.

Data and storage

.byte emits individual bytes. .word emits a little-endian word, including label addresses. .res uses a decimal count and optional decimal fill byte, such as .res 16,0. Reserved bytes are part of the linked output and count towards its 32768-byte maximum. Use a label to address owned storage, not an arbitrary unused-looking address near BASIC’s variables.

The source validator also bounds the source file to 128 KiB and an assembly source line to 4096 bytes of ASCII. Operands are restricted to the supported expression character set. These bounds prevent arbitrary build scripts; they are not a statement that every accepted operand is meaningful. ca65 performs the final instruction/mode/range checks.

Return safely

A SYS-started routine inherits a live BASIC/KERNAL machine environment. Keep its stack balanced, leave decimal mode clear for BASIC, and preserve any zero-page or system state you borrowed. The supplied examples avoid disabling interrupts or changing the CPU memory port. If you change colours or display contents, that visible change may intentionally remain after RTS; distinguish that from corrupting the interpreter’s workspace.

Do not reset the stack pointer with TXS, replace the IRQ vector, bank out ROM or install an endless interrupt handler as part of these beginner routines. Studio’s accepted release scope does not provide a debugger or a bank-switching workflow. Use Stop to recover from a stuck machine-code programme, fix the source and Run a fresh build.

Useful build diagnostics

An unsupported directive is rejected before tools run. An invalid addressing mode or immediate value can be rejected by ca65. A branch outside its signed-byte range needs a different control-flow sequence, not a larger BASIC line number. Missing or incompatible tools require Settings changes. After any failure, read the diagnostic and rebuild; Run never falls back to a previous successful PRG.

Assembly loops, tables and routines

Counted loops must define their bounds

An 8-bit index can represent 0–255 and wraps after that. For a table with five items, initialise X to zero, access item X, increment X, compare against five and repeat while unequal. A decrement-to-zero loop has different entry behaviour: starting X at zero and immediately executing DEX produces 255, not an empty loop. Pre-test when zero items should mean no work.

Put the count next to the design of the data. A zero-terminated string uses a different rule: fetch a byte, stop on zero, otherwise output it and advance. Such a scan must still remain inside the allocated table if its terminator is damaged or missing. For small fixed demos, an explicit count often makes the boundary easier to verify.

Save only the state the caller needs

.org $080D
    ldx #7
    jsr print_mark
    txa
    clc
    adc #48
    jsr $FFD2
    lda #13
    jsr $FFD2
    rts
print_mark:
    txa
    pha
    lda #42
    jsr $FFD2
    pla
    tax
    rts

Expected result: *7 and a line break. The routine preserves X by transferring it to A and pushing it. It does not promise to preserve A or flags. The caller uses X after the call, demonstrating that preservation is part of a useful routine contract rather than ceremonial code.

Write down each routine’s inputs, outputs and changed registers. A routine that accepts A as a character can return with A changed if that is documented. A table-walking caller that keeps its index in X must preserve it around calls that can change X. Pushing A after a transfer saves the transferred value, not the earlier accumulator contents; choose the save order consciously.

Words and pointers

A pointer is a stored address, usually two bytes in little-endian order. Indirect-indexed access LDA (pointer),Y requires the pointer itself in zero page. The pointed-to data can be elsewhere. Incrementing Y walks at most a 256-byte offset range before it wraps, so a longer transfer must advance the pointer or use another bounded layout.

In a C64 programme, reserve and preserve a permitted zero-page pair before using it. The conventional user bytes $FB–$FE are small; they are not a licence to overwrite neighbouring BASIC workspace. A routine called from another routine must also respect that caller’s use of the pair. If absolute indexed addressing is enough, it avoids borrowing a pointer entirely.

Read-only data versus writable state

A table of character codes may remain unchanged throughout a run. A counter, score or current position is writable state. Give each a label and choose its width. Keep both after a return or behind a jump so the processor cannot fall into data. The C64 PRG is loaded into RAM, but that does not make accidental self-modification a good beginner technique.

When copying overlapping ranges, direction matters. Copying forwards from a lower address into a nearby higher address can overwrite bytes that have not yet been read. Copy backwards or choose disjoint ranges. Also keep the copy away from the current instruction stream, stack, interpreter state and hardware registers.

Make failure visible and recoverable

For a small assembly exercise, use one border colour for a successful self-check and another for failure, then RTS. This provides a bounded observation without embedding debugger assumptions. Test the zero count, final item and carry boundary explicitly. If a loop waits for an external event, give it an exit path or a finite iteration budget rather than treating a hang as useful output.

Delay loops count instructions, not wall-clock milliseconds. Their duration varies with CPU timing and C64 video contention. Keyboard and the normal clock rely on interrupt service, so leaving interrupts disabled can make a seemingly reasonable input loop wait forever. Use the default machine environment while learning and keep timing-sensitive experiments separate from general routine examples.

Screen and colour addresses

With the default screen matrix, the cell at column X and row Y is 1024+40*Y+X. Its colour is at 55296+40*Y+X. X ranges from 0 through 39 and Y from 0 through 24. The corresponding assembly bases are $0400 and $D800. Use a screen code for the first write and a colour value 0–15 for the second.

A PETSCII A has code 65, while screen code 1 selects A in the standard uppercase/graphics set. Printing through BASIC or CHROUT performs a character-output interpretation; storing a byte directly into screen RAM does not. Misunderstanding this difference produces unexpected symbols even when the address arithmetic is correct.

Video-bank boundaries

The VIC-II sees a 16 KiB bank selected by machine registers, and screen, character and sprite addresses are interpreted within it. The examples retain the default bank and screen setup. A sprite pointer holds a 64-byte block index within that bank, not a full CPU address. Eight sprite pointer bytes are located relative to the screen matrix, not at universal addresses after arbitrary screen relocation.

The sprite tutorial deliberately uses $0340–$037F in the normal cassette-buffer region after PRG RAM injection, while cassette devices remain unused. That is a stated allocation with a matching pointer, not general free memory. It would be unsuitable if a different workflow needed the cassette buffer. Do not move the CPU or VIC bank to make copied listings fit: bank switching is outside the current Studio scope.

Read hardware registers with care

Some hardware values contain status bits, unused readback bits or side effects on read. Mask the low nibble when interpreting a colour register. A register that acknowledges an event or triggers hardware is not a RAM variable. Avoid INC, DEC and other read/modify/write instructions on I/O unless the documented bus effects are exactly what is intended.

The CIA keyboard matrix and joystick lines share circuitry. Advanced direct scanning needs a clear plan for data-direction registers, output bits and the KERNAL keyboard service. The beginner input examples use GET or GETIN so they can leave that machine state under normal system control.

140 POKE 53287,7:POKE 53269,1
150 PRINT "SPRITE DEMO - PRESS Q TO FINISH"
160 GET K$:IF K$<>"Q" THEN 160

Expected result: a yellow pattern of vertical stripes, with a thicker pair in the centre. Q hides it and returns to BASIC. Each loop writes one row’s three bytes; the data deliberately repeats a simple pattern so you can calculate each bit. The setup clears shared sprite-mode registers because this is a fresh, single-sprite demo. In a multi-sprite programme, preserve the other sprites’ bits with masks instead.

Design your own image

Draw a 24×21 grid on paper. For each eight-pixel group, add 128, 64, 32, 16, 8, 4, 2 and 1 for the pixels you want lit. Store three values per row. A data-driven version can READ those 63 values from DATA and POKE them into the same block. Check the item count before enabling the sprite so an OUT OF DATA error does not leave partly initialised graphics.

The image pointer is not an arbitrary absolute address divided by 64 when the video bank changes: it is a block index within the selected 16 KiB VIC bank. This guide keeps the default mapping. Placing data at $C000 while keeping pointer 13 would not point to it. Do not change bank registers to make an unrelated listing fit the current source workflow.

Movement and multiple sprites

For movement, update low X and Y from bounded variables. When crossing X=255, split X into its low byte and the appropriate high-bit mask in $D010. Each sprite occupies its own bit in enable, expansion, multicolour and priority registers. Set one bit using OR and clear one using an AND mask that preserves the other seven bits.

Multicolour sprite mode interprets pixel pairs and combines shared and per-sprite colours, reducing horizontal colour-detail resolution. It is a different data format from the single-colour example. Work through one original image and its expected bytes before switching modes.

Collision and cleanup

Registers $D01E and $D01F provide sprite/sprite and sprite/background collision masks. Their read behaviour clears latched collision information, so save a read result if several parts of the programme need it. Hardware overlap is only one input to game rules; it does not decide which object takes damage or whether a collision has already been handled.

On a normal exit, disable sprites owned by the programme and restore changed modes if the caller expects them. If you interrupt the example before its final lines, the sprite can remain visible until you hide it or restart. A fresh Studio Run resets the session; it does not preserve a game’s score or object positions.

C64 sound programming

Sound is a register programme

BASIC V2 has no SOUND statement. The C64 SID chip has three voices controlled through memory-mapped registers. Each voice has a frequency word, pulse-width fields, a waveform/control byte and envelope settings. A shared volume/filter register controls the overall mix. Begin with one voice and a simple waveform, then build towards multi-voice effects.

Voice 1 addressPurpose
54272 / 54273 ($D400/$D401)Frequency low and high bytes.
54274 / 54275 ($D402/$D403)Pulse width low byte and high nibble, relevant for pulse waveform.
54276 ($D404)Waveform/control byte, including the gate bit.
54277 ($D405)Attack high nibble, decay low nibble.
54278 ($D406)Sustain high nibble, release low nibble.
54296 ($D418)Master volume in the low nibble, with filter/voice-control bits above it.

Voice 2 uses the same seven-register pattern starting at $D407 and voice 3 at $D40E. SID registers are not all readable mirrors of their last written values. Keep your intended sound state in variables rather than trying to recover it by PEEK from every write-only register.

Pitch and the PAL clock

A 16-bit frequency value controls the oscillator. Approximately, frequency in hertz equals the register value times the SID clock divided by 16777216. For the PAL C64 clock of about 985248 Hz, a register value near 7493 produces approximately 440 Hz. Split the integer into low byte F AND 255 and high byte INT(F/256). Different clock standards change the result, which is why this guide labels the PAL assumption.

A pitch table can hold pairs of low/high bytes. Change pitch by writing both bytes in a deliberate order, accepting that there is a short intermediate state. Do not put a value above 255 into one byte because the overall frequency is larger; it is the two-byte word that represents the complete setting.

Waveform, gate and envelope

The usual waveform bits are triangle 16, sawtooth 32, pulse 64 and noise 128. Gate is bit 0. Triangle with gate on is therefore 17; clearing the gate while retaining triangle gives 16. Other control bits have specialised uses such as synchronisation, ring modulation and test. Avoid enabling them accidentally through an unexplained decimal constant.

Attack, decay and release select rate settings; sustain selects a level. The rate nibbles are not millisecond values. Gate on starts the attack/decay/sustain progression and gate off starts release. Master volume zero silences the mix; a note can be configured correctly yet remain inaudible if volume is zero. Pulse waveform also needs a sensible non-extreme pulse width.

10 FOR I=0 TO 24:POKE 54272+I,0:NEXT I
20 POKE 54296,8
30 POKE 54277,17:POKE 54278,129
40 F=7493
50 POKE 54272,F AND 255
60 POKE 54273,INT(F/256)
70 POKE 54276,17
80 FOR T=1 TO 600:NEXT T
90 POKE 54276,16
100 FOR T=1 TO 300:NEXT T
110 POKE 54296,0
120 END

Expected result: one moderate-volume triangle tone, a release period and silence. The loop counts give an audible demonstration, not a calibrated duration. The initial loop resets the SID’s programmable register range for this fresh demonstration and would erase another programme’s active sound state. Avoid doing that in a larger programme that owns several independent voices.

Build a short effect

To make a rising effect, step a bounded frequency variable and update both frequency bytes while leaving gate on. To play separate notes, clear the gate, allow a release interval, choose the next frequency and start the gate again. Abrupt envelope restarts can have chip-specific behaviour; do not assume a sampled instrument model or perfect retrigger timing.

For noise effects, select the noise bit with a deliberate gate value and keep the same volume/envelope discipline. Combined waveform behaviour and SID revisions can change the timbre. The current examples demonstrate register use; they do not claim identical sound across every SID implementation or emulator setting.

Silence on exit and diagnose methodically

Clear gates and return master volume to an appropriate value when the programme ends. If you interrupt before cleanup, enter POKE 54296,0 yourself at READY or stop the emulator. First check VICE audio output and host volume, then the master volume, waveform, gate, envelope and frequency. A live VICE process or successful PRG build does not establish audible output.

Music timing should use a deliberate update cadence rather than unbounded busy loops. Advanced interrupt-driven playback needs careful register/stack preservation and ownership of the machine’s interrupt service. It is beyond these initial SYS-returning examples and must not be copied into a BASIC project without a compatible memory and lifecycle plan.

Calling the C64 KERNAL

Call a documented interface

The KERNAL is the C64’s operating-system ROM. Its jump table provides stable entry addresses for supported services, avoiding calls into arbitrary internal implementation locations. An entry address alone is not a complete interface: check required registers, flags, channel setup, results and changed state. These notes assume the normal C64 ROM mapping and the firmware revisions supported by Studio.

In the restricted source format, call an entry with its numeric address, such as JSR $FFD2. The uppercase service name in this article explains that address; it is not automatically a predefined ca65 symbol. Do not paste assembler equates or include directives from another project into Studio’s single-source subset.

Keyboard polling

GETIN is a non-blocking keyboard-queue read under the default input configuration. Test A for zero and return to useful work when there is no input. Do not keep an index in X across the call unless you save it. Unlike a raw matrix scan, the queue is maintained by the normal KERNAL interrupt service. SEI followed by waiting for newly scanned keyboard input is therefore a poor default design.

A robust interactive loop has a quit key and a state update, not just an endless wait for one exact byte. If you need a delay, a timer-driven update or a finite counter should still allow input handling. Studio Stop remains the recovery path when a machine-code error prevents normal input.

Service boundaries

KERNAL file routines still depend on a real device/channel setup. Their addresses do not override Studio’s disabled disk, filesystem, printer and remote-monitor settings. Do not call ROM initialisation routines or reset vectors as convenient substitutes for cleaning up only the state your programme changed.

The reference manual contains a full KERNAL catalogue for further study. Before using a new service, write a small caller with defined inputs and visible output, verify the exact supported ROM contract, and keep its stack/register effects documented. An arbitrary ROM address found in a listing from another Commodore machine is not automatically a C64 API.

BASIC project: collect the stars

What you will build

This original character-cell game combines input, bounded movement, state and screen output. Move the A character left and right with A and D. Collect the star five times, or press Q to finish early. It deliberately stays on one row so you can understand the complete update loop before adding vertical movement or obstacles.

Create a BASIC project and replace the entire configured source with the listing. Save and Build, then Run with the configured VICE setup. Focus the emulator window before pressing keys. The player starts at column 5; the first star is at column 25. Both are on row 12 of the default screen.

10 PRINT CHR$(147)
20 POKE 53280,6:POKE 53281,0
30 X=5:Y=12:TX=25:SC=0
40 PRINT "A/D MOVE   Q QUIT   COLLECT FIVE STARS"
50 GOSUB 1000
60 GET K$:IF K$="" THEN 60
70 IF K$="Q" THEN 300
80 OX=X
90 IF K$="A" THEN X=X-1
100 IF K$="D" THEN X=X+1
110 IF X<1 THEN X=1
120 IF X>38 THEN X=38
130 POKE 1024+40*Y+OX,32
140 IF X<>TX THEN 180
150 SC=SC+1
160 TX=39-TX
170 IF SC=5 THEN 300
180 GOSUB 1000
190 GOTO 60
300 PRINT CHR$(19)
310 PRINT "FINISHED - SCORE";SC;"                 "
320 END
1000 POKE 1024+40*Y+TX,42
1010 POKE 55296+40*Y+TX,7
1020 POKE 1024+40*Y+X,1
1030 POKE 55296+40*Y+X,1
1040 RETURN

Separate state from presentation

X is the player column, Y is the fixed row, TX is the star column and SC is the score. These variables are authoritative; the screen is a presentation of them. OX remembers the old player position long enough to erase it. The drawing routine reads state and writes cells without changing the score.

Lines 60–120 read input and constrain movement. Lines 130–170 erase the old cell and apply collision/scoring rules. The drawing routine paints the target and player at their updated positions. This order avoids leaving a trail and keeps a collision from incrementing the score more than once before the star moves.

Why the boundaries matter

The player is limited to columns 1–38, leaving a margin and preventing writes past the intended row. Unknown keys leave X unchanged. GET returns an empty string when idle; the loop handles that without calling ASC or changing state. The target alternates between 25 and 14, so collecting it moves it away from the player.

END separates main execution from the GOSUB routine. Without it, normal fall-through would reach RETURN without a saved call. The subroutine writes both screen code and colour; setting only one can leave a correct symbol with an old, hard-to-see colour.

Check the complete journey

First press an unrelated key and confirm that the player does not move. Move left repeatedly and confirm it stays at column 1. Move right repeatedly and confirm it stays at 38. Collect the star: it should reappear at the other target column. Continue until the fifth collection; the top line should display FINISHED and score 5. Start a fresh Run and press Q before collecting anything; it should finish with score 0.

These are runtime checks to perform in VICE. A successful BASIC encoding test cannot prove the screen positions, keyboard mapping or game rules. If a check fails, reduce the listing to one input or drawing operation, fix that observation, then restore the complete loop.

Extend it in small steps

First add a score display in a fixed area, taking care that PRINT does not scroll or overwrite the game row. Next add W/S movement with a stored previous Y and limits of rows 2–22. Finally choose a new star position using RND, rejecting the player’s current cell. Each addition should preserve the quit key, bounds and clean end state.

For obstacles, store the board in an array and consult it before moving. Restore the old tile when erasing the player rather than always writing a space. For a sound effect, call a small bounded SID setup/cleanup routine when a star is collected; avoid a long blocking delay that makes keyboard controls feel unresponsive.

Save a working source revision before each exercise. If using Git, make the commit yourself through the authorised source-control action. Rebuild on save restarts the game and loses its current score; turn it off when testing a longer running session.

Assembly project: a text banner

A visible programme with an explicit exit

This original exercise clears the screen, writes a coloured banner directly into screen RAM, and waits for Q before returning to BASIC. It uses two character representations deliberately: the banner table contains screen codes, while Q is read as a keyboard character through GETIN. The polling loop leaves the normal interrupt service enabled.

.org $080D
    lda #147
    jsr $FFD2
    lda #0
    sta $D021
    ldx #0
paint:
    lda banner,x
    sta $0597,x
    lda #7
    sta $D997,x
    inx
    cpx #9
    bne paint
poll:
    jsr $FFE4
    cmp #81
    bne poll
    lda #13
    jsr $FFD2
    rts
banner:
    .byte 3,54,52,32,19,20,21,4,25

Expected result: C64 STUDY in yellow on a black background, beginning at row 10, column 7. Q returns to READY. The banner base is $0400+10*40+7=$0597; the matching colour address is $D800+10*40+7=$D997. Nine table entries match the CPX #9 bound.

Follow one iteration

X initially selects banner byte zero, screen code 3 for C. STA $0597,X writes it to the first banner cell. Loading 7 and storing it to $D997,X sets that cell’s yellow colour. INX advances to the next item. CPX #9 sets the flags for BNE; the branch repeats until every index 0–8 has been used.

The table follows RTS, so normal control cannot fall into it. Its bytes are still part of the PRG payload and are loaded with the instructions. A table label supplies an address, not the first table value. LDA banner,X reads the selected byte; LDA #<banner would load only part of its address and produce a different result.

Input has its own lifetime

The paint loop completes before GETIN is first called, so no live X index is carried across that routine. GETIN returns zero when no key is ready; CMP #81 simply leaves the polling loop active for zero or any key other than Q. The example owns no borrowed zero-page pointer and makes no change to the stack pointer or IRQ vector.

Waiting for Q is intentional and user-controlled. Studio Stop can always terminate the owned process if the programme is changed into a stuck loop. A fresh Run rebuilds and starts from a clean session. Do not mistake the Running label for proof that the banner reached the screen.

Inspect build and memory assumptions

The source begins at $080D and relies on Studio’s generated SYS loader. It uses only .org, documented instructions, a simple label and .byte. The display addresses assume the standard screen/VIC bank. There is no separate BASIC source to edit, no imported module and no custom linker configuration.

If a copied banner displays odd symbols, compare each table byte with the intended screen code. Alphabetic screen codes 1–26 represent uppercase A–Z in the default mode; digits use their appropriate screen-code values, and 32 is a space. A quoted ASCII string is appropriate for the CHROUT example but is not a drop-in replacement for this direct screen-code table.

Verification checklist

Build with the configured compatible ca65/ld65 and confirm the PRG is current. Run it, verify the nine-character text, colour and position, then press an unrelated key and confirm it stays active. Press Q and confirm BASIC resumes. Run again and confirm the initial result is repeatable. If you change the table length, change and recheck the loop bound together.

Assembly verification checks that the source is accepted and linked bytes are produced. The programme’s display/input checks are separate emulator observations. Studio currently exposes no source debugger, breakpoint view or register-step workflow for C64, so the tutorial does not depend on one.

Three useful exercises

Change the banner to another short word, calculating its screen codes and count. Then add a second row with its own table and bound. Finally let a key cycle the text colour using a stored byte restricted to 0–15. Keep Q as an exit, avoid carrying unsaved registers across KERNAL calls and leave the stack balanced.

For a more general text routine, pass a pointer and length under a written calling convention and preserve any borrowed zero-page bytes. Test empty and maximum-length cases as well as the ordinary message. That is a useful next step after the fixed banner is understood; it is not a reason to add unsupported assembler macros or multiple source modules.

Check the single-source subset first. ca65 can then reject an operand, addressing mode, range or unresolved label. A relative branch that has become too far away needs a shorter branch path or an inverse branch around JMP. A .res operand must use a decimal count and optional decimal byte fill. Equates, included modules and custom linker segments from an external ca65 project are not accepted merely because ca65 itself knows them.

Keep evidence specific

Record the source revision, complete example, tool versions and what appeared in VICE. A successful build is an encoding/linking result. A Running badge is process supervision. A screenshot establishes only what was visible at that moment; audio and input need their own observations. Physical C64 behaviour, Intel Mac compatibility and signed public distribution remain separate checks.

If you need to share a problem, reduce it to a small original programme with the same failure and include the stable diagnostic. Do not attach firmware bytes, private provider payloads or a commercial programme. Keep the working source before making experimental changes, and never repair a failed build by manually replacing generated output with an older successful file.

Use references critically

The original C64 manual is a technical reference, not a current Studio installation guide, and historical publications can contain errors. Check related sections when a table conflicts with explanatory text. In particular, the 6510 port data-direction register is at $0000 and the port at $0001; do not reverse them because of a conflicting historical description.

The processor chapter distinguishes NMOS from CMOS behaviour. Examples from 65C02 or 65816 manuals can include unsupported instructions and different decimal/interrupt details. Likewise, BASIC examples from a C128, Plus/4, Dragon or a modern BASIC may contain commands absent from C64 BASIC V2.

What is verified

Complete BASIC listings in this guide are checked by the native encoder. Complete assembly listings are checked by the native source policy and an opt-in compatible ca65/ld65 build. These checks establish encoding and assembly acceptance, not full BASIC runtime syntax or successful video, audio and input. Each tutorial states the expected observation separately so it can be tested in a real emulator session.

The Help generator and product tests check article metadata, links, language coverage and searchable content. The same source generates the in-app pages and macOS Help Book resources. Keep edits in the Commodore-owned source guide and manifest rather than changing a generated page that will be overwritten.
